# Design-system audit of the current UI (2026-10-27)

Branch `pilot/DESIGNAUDIT-297`, base `origin/main` 1b0ddd85c (v2.23.2). Read-only on product code. This is the first step
toward ONE design system; the foundations are written in parallel (Fable) and read this file as it lands.

Status of this file: **v2** - code inventory (§1-2), rendered capture matrix and probe (§3), per-screen critique (§4), the
severity-ranked findings (§5), the token / skin inventory table (§6) and the recommendations for one token contract and the
component rules (§7). §0 is the one-page summary.

## 0. Summary

**Verdict.** The product has a good token table (`design/tokens.ts`, 261 tokens, light + dark, contrast-tuned) and a mature
RTL practice, but **not a design system**: around it sit twelve-plus parallel styling layers (skins, 13 look dials, palettes,
the MD1 material formula, the `--dv-*` glass family with its own 4 palettes / density / dark switch, and per-screen knob sets
`--mm --mr --nt --ab --sc --lv --wall ...`) that each re-decide colour, shape, type and size. The skins themselves change
almost nothing structural: across 4 live skins x 2 schemes the 25 captured screens keep the same layout, and differ in canvas,
radius, blur and accent only. The rendered evidence shows the cost of the layering: a selected control whose label is invisible
in dark mode because two knob families meet (P1-3), white-on-colour status pills at 1.8-3.8:1 in the infra reference screen
(P1-2), two typefaces depending on the screen (P1-1), and up to five rows of controls before content on service management
(P1-5).

Impeccable audit health score (technical, 0-4 each): Accessibility **2** (contrast misses on state pills and a dark-mode
control, 21-100 sub-44 px targets per desktop screen) · Performance **3** (blur stack up to 40 px, no `will-change`, lite tier
exists) · Theming **2** (tokens exist and are used 17k times, but 594 literal fallbacks, 43 ghost tokens, 8.9k literal spacings,
two dark switches) · Responsive **3** (no horizontal overflow anywhere at 390 px, phone dock and touch sizes exist; heavy
vertical stacking) · Implementation integrity **2** (systemic drift through parallel knob layers) = **12 / 20, "acceptable,
significant work needed"**. The work is a consolidation, not a rescue.

Top five for the new foundations:
1. ONE token contract with three tiers (reference -> semantic -> component), every knob family folded in or renamed as a
   component tier of the same contract; skins = semantic-tier values only (§7.1).
2. A real spacing / size scale (4 px grid) and a control-size scale with the 44 px target built in (§7.2).
3. One type ramp of 6-7 steps on one family (Heebo, 400-700 only), no half pixels, plus a display tier (§7.3).
4. State colour pairs that are always used as pairs (fill + on-fill text), enforced by the lint (§7.4).
5. Component rules for the page header / tab pair, filter bar, segmented control, status pill, KPI tile, card, list row,
   tree panel and the empty / loading / error panel, so operator screens stop assembling these by hand (§7.5).

Owner rules this audit respects and measures against: UniFi-Protect-style direction; no scrolling in control screens; clean
operator screens (no hints / badges / paragraphs); the floors / areas tree survives every design; no Home Assistant branding
outside Settings; mockups in the infra-screens look (temperature / elevators / schedules); Hebrew RTL first, video / map /
3D / timeline never mirrored.

Method (reproducible): a regex scan of every `.ts` / `.css` file under `frontend/src` (1,194 files: Lit `css\`` blocks are in
`.ts`), plus a read of `design/tokens.ts`, `design/skins/*`, `design/look.ts`, `styles/devices-themes.ts`,
`styles/devices-palettes.ts`, `docs/design/DEVICE_THEMES.md`, `docs/design/DU1_DESIGN_UNIFICATION.md`. The scan scripts are
not committed (scratch); every number below names what it counted so it can be re-run.

## 1. What exists: the theming layers

that each re-decide colour, shape and size. Each layer is individually documented and tested; the problem is their sum.

Consequences, measured:

- **Combinatorics no one can test.** A device screen's pixels depend on skin (4 live) x scheme (2) x `devices.style` (2) x
  `devices.theme` (4) x `devices.scheme` (3, resolved with `ui.scheme`) x `devices.density` (2) x `ui.tile_layout` (3) = 1,152
  combinations before the look dials. The visual matrix (`frontend/tests/visual/matrix.json`) covers 11 screens in the
  **classic** skin only, light + dark.
- **Two "dark modes".** `ui.scheme` drives `--sw-*`; `devices.scheme` drives `--dv-*` and is resolved in JS
  (`applyDevicesScheme`). DU1 bound them (glass is never lighter than the shell) but they remain two switches with two sets of
  values.
- **Two radius systems.** Product radii (classic `--sw-r-md` 12) vs glass knobs (`--dv-radius-md` 22, `-lg` 28). DU1 §4 left
  this open as an owner decision; it is still open.
- **Skins are half-skins.** A skin overrides ~110 of 261 tokens and ~35 rules on ~16 hosts. Everything inside a glass screen is
  re-pointed by `--dv-*` after the skin has spoken, so a skin cannot fully restyle home, schedules, media or notifications.

### 2.2 Colour

- `--sw-*` covers surfaces (3 levels + solid twins + menu), 5 text tiers, accent set, 10 state colours each with `-soft` and
  `-text`, video HUD, map / object palette. Well structured; the contrast work of UXFIX-A11Y-295 lives here.
- Literal colours still in source: **1,773 hex** (808 distinct) and **893 rgba()**. Half sit in legitimate data
  (`tokens.ts`, skins, `devices-palettes.ts`: `design/` holds 688 hex). Outside the token / palette files the largest owners
  are `notice-tv/tv.css` (253 literal points), `components/media-remote-css.ts` (194), `wall/sw-wall.ts` (182),
  `components/sw-scene.ts` (176), `public-ticket/styles.css` (109), `styles/media-glass.ts` (104), `map/skin-control.ts` (53),
  `shell/sw-app.ts` (53).
- **594 `var(--token, <literal>)` fallbacks** (237 in `screens/`, 108 in `wall/`, 92 in `components/`): each one is a second
  value for the same decision and silently wins when a token is renamed.
- **43 ghost tokens**: names referenced with `var()` that are set nowhere (not in `tokens.ts`, not by any skin, knob or
  script), so their fallback literal always renders. Examples: `--sw-text-muted` (7x), `--sw-warning-bg` (3), `--sw-line` (3),
  `--sw-error` (2), `--sw-space-2/3/4`, `--sw-radius-sm`, `--sw-text-sm`, `--sw-text-1`, `--sw-text-4`, `--sw-primary`,
  `--sw-shadow-lg`, `--sw-online`, `--sw-success-bg`, `--sw-danger-bg`, `--sw-warn`, `--sw-warn-text`, `--sw-z-popover`,
  `--sw-surface-sunken`, `--sw-on-solid`, `--sw-accent-on`, plus the 9 `--sw-dd-*` hooks of `sw-dropdown` (undocumented
  public knobs). They show where authors guessed a token name: the contract is not discoverable at the point of use.
- **84 component-local knobs live in the `--sw-` namespace** (`--sw-float-reserve`, `--sw-lead-reserve`,
  `--sw-settings-row-h`, `--sw-el-*` elevator states, `--sw-gw-*`, `--sw-dw-*`, `--sw-card-*`, `--sw-kpi-*` ...). They are
  fine as knobs but indistinguishable from product tokens by name.
- 20 declared tokens are never referenced (`--sw-nav`, `--sw-touch`, `--sw-s-10`, `--sw-z-map`, `--sw-surface-3-solid`, half
  of the `--sw-obj-*` and `--sw-hue-*` sets ...).

### 2.5 Motion (code, `review-animations` / emil-design-eng criteria)

- Token durations 120 / 200 / 220 ms with `cubic-bezier(0.2, 0, 0, 1)`: crisp, right for an operator product.
- Literal durations escape the reduced-motion zeroing in `css.ts` unless the file has its own query (82 files do).
  Long loops (1.2-3 s pulses, 12 s / 28 s / 60 s ambient loops) exist in 30+ places; they need an explicit reduced-motion
  alternative, not only the global 0.01 ms kill (4 places).
- Overshoot thumb easing `cubic-bezier(.34, 1.3, .64, 1)` in domus / crystal / bubble (flagged by the Impeccable detector as
  bounce easing); acceptable on a toggle thumb only, never on panels.
- 367 `:hover` rules, only 9 gated by `@media (hover: hover)`: hover washes and the domus tile lift fire on tap on phones.
- 56 `:active` rules, 5 with press feedback (scale): most buttons give no press response; the shared button should own it.
- No `transition: all`, no `scale(0)` entries, no `will-change` (good).

### 2.6 Impeccable detector (`impeccable detect --json frontend/src`)

20 findings: 17 "side-tab" thick inline-start borders (3-4 px) on cards and rows (`home-widget.ts:55`,
`infra-elevators.ts:88`, `gen-styles.ts:522`, `sw-schedule-grid.ts:365`, `plan-studio-panel.ts:1690`, `system-wizard.ts:404`,
`calendar-view.ts:220`, `overview-tab.ts:224`, `sw-dropdown.ts:678`, ...), 3 bounce easings (the skins' thumb curve). The
side stripes are used as state colour on cards; the new contract should give state one shape (dot + pill, or a full tinted
card) instead of a 4 px stripe in some screens, a tinted border in others (elevators / temperature) and a wash in a third
(home floor rows).

## 7. Recommendations: one token contract and component rules

These are inputs for the foundations work, written to respect the owner rules (UniFi-style operator look, infra-screens
look for mockups, tree kept, no scrolling in control screens, clean operator screens, no HA branding, RTL first).

### 7.1 The contract: three tiers, one namespace per tier

1. **Reference** (`--ref-*`, never read by components): the raw palette (neutral 0-1000 ramp, blue, green, amber, red,
   violet ramps), the 4 px space unit, the radius set, the type sizes, durations / curves. Light and dark are two reference
   maps.
2. **Semantic** (`--sw-*`, the only tier screens read): surface (canvas, base, raised, overlay, sunken, menu = always
   opaque), border (subtle, default, strong), text (primary, secondary, tertiary, disabled, on-accent, on-state, on-video),
   accent (fill, fill-hover, soft, text, focus), state x {fill, soft, text, on-fill} for success / warning / danger / info /
   neutral / offline / live / recorded, space `--sw-space-0..12`, size `--sw-control-sm/md/lg`, `--sw-hit` (44), radius
   `--sw-radius-xs..xl` + `pill` + `media`, elevation `--sw-elev-0..3`, type roles (`display`, `title`, `heading`, `body`,
   `body-strong`, `label`, `caption`, `numeric`), motion (`--sw-dur-instant/fast/base/slow`, `--sw-ease-standard/enter/exit`),
   layers (`--sw-layer-base/sticky/dropdown/overlay/modal/toast`), breakpoints (documented constants: 600 / 900 / 1200).
3. **Component** (`--c-<component>-*`, e.g. `--c-kpi-value-size`, `--c-seg-thumb`, `--c-seg-thumb-text`): defined only from
   semantic tokens, declared in the component file, documented in one generated list. This is where today's `--dv-*`,
   `--mm-*`, `--mr-*`, `--nt-*`, `--ab-*`, `--sc-*`, `--lv-*`, `--wall-*` and the 84 `--sw-` component knobs go.

Rules: a **skin = one semantic map (light + dark) + at most a handful of component-tier values**, no CSS rules except a
small, budgeted set of material rules (glass, sheen) that read semantic tokens; a skin never changes layout, density or
structure. **One scheme switch** (`ui.scheme`), resolved on `:root`; `devices.scheme` and the glass palettes become
semantic maps or are retired. **No fallbacks in `var()`** (the token list is generated and typed, so a missing token fails
the lint instead of silently rendering a literal). Retire the look dials that no live skin reads, or make them semantic
overrides every skin honours.

### 7.2 Space and size

- Space scale on a 4 px grid: 0, 2, 4, 8, 12, 16, 20, 24, 32, 40, 48, 64 (12 steps; 2 px only for hairline offsets). Map the
  current top literals: 8 / 12 / 16 / 4 / 24 stay; 10 -> 8 or 12, 6 -> 4 or 8, 14 -> 12 or 16, 18 -> 16 or 20 by context.
- Control heights sm 32 / md 36 / lg 44 with the hit area always >= 44 x 44 (pseudo-element expansion on the compact ones)
  in every skin, not only bubble.
- Page padding 24 desktop / 16 phone; card padding 16 / 12; grid gaps 16 / 12.
- Lint: no px in gap / padding / margin outside the token file (allow 0, 1, 2 px hairline cases with a reason).

### 7.3 Type

- One family: Heebo (shipped weights 400 / 500 / 600 / 700); mono for IDs only. Never re-point the family per screen.
- Seven roles on integer sizes: caption 12, label 13, body 14, body-large 16, heading 18, title 22, display 28 (+ numeric
  display 40 / 56 for clocks and gauges). 11 px only for dense chart axes, never for labels of controls (phone dock -> 12).
  Line heights per role (1.25 headings, 1.45 body); tracking only on display and numeric roles.
- Lint: no literal font-size / weight / line-height / letter-spacing outside the type tokens.

### 7.4 Colour and state

- Every state has four tokens and they are used as pairs: `fill` + `on-fill` (solid badge), `soft` + `text` (soft chip),
  bare colour only for dots / bars / icons. The temperature badge (P1-2) and the tickets "urgent" chip are the test cases.
- Each skin's semantic map is generated and checked for contrast (text >= 4.5:1, large / icons >= 3:1) on its opaque
  surfaces, and on its glass surfaces against the worst point of its canvas (extend `tests/unit-muted-contrast.spec.ts`).
- One accent per skin; decorative hues (`--sw-hue-*`) only on home / media art, never meaning.

### 7.5 Component rules (the operator-screen kit, in the infra-screens look)

The elevators / temperature / schedules screens are the reference: page header, a KPI row, then cards or a list.

1. **Page header** (one component): title + optional subtitle line at the inline start; actions at the inline end on the
   same row (max one primary + one secondary + overflow menu); the area tab pair above it. Brand lives in the rail / dock,
   not in every page header on phone. The title does not repeat the rail label when the area has only one page.
2. **Tab pair**: area tabs (pill) + page tabs (underline) is the only two-level navigation; a third level becomes a side tree
   (settings) or a segmented control inside the content, never a third tab row. Overflowing tabs collapse into a "more" menu,
   never clip mid-word.
3. **Filter bar**: one row: search, one segmented scope (max 4 options), a "filter" button that opens a sheet with
   everything else, view switch at the end. Chip groups with counts go into the sheet. Tickets / board must fit this.
4. **KPI tile**: one shape: value (numeric role) over label, state dot at the inline start, optional delta line; tile =
   button when it filters; selected = accent ring. Max 6 per row on desktop; on phone a single horizontal strip (2.5 tiles
   visible) instead of 3 stacked rows.
5. **Status**: dot + text for lists, solid pill (`fill` + `on-fill`) for the card's main state, soft chip for secondary
   attributes. No side stripes; a card is tinted by state only for alarm-level states, never for normal.
6. **Card**: radius `md`, padding 16, elevation 0 or 1 by skin, header row (title, subtitle, status, overflow menu), body,
   footer meta row in caption role. Long names: one line + ellipsis + full name in `title`.
7. **List row / table**: 44 px minimum row height, numbers tabular and end-aligned in RTL, one hover wash gated by
   `(hover: hover)`, row actions in an overflow menu.
8. **Segmented control** (one component, replaces the 87 private ones): track = `surface-sunken`, thumb = `surface-raised`,
   thumb text = `text-primary` of the same scheme (fixes P1-3 by construction).
9. **Tree panel**: the floors / areas tree has one component and one width scale (desktop 240-320, collapsible with a
   control placed on the tree itself; phone: a sheet opened from the header).
10. **State panel**: empty / error / forbidden / stale / partial as today; loading = a skeleton of the target layout;
    vertically centred in the content area; no paragraphs beyond one line.
11. **Overlays**: dialog (confirm / short form), sheet (phone and long forms), popover / menu (always opaque). Drawer only for
    record detail. One motion each (enter 200 ms ease-out, exit 150 ms).
12. **No-scroll layouts**: control screens size their grids to the viewport (rows = what fits, pager for the rest, as
    schedules and the wall already do); only lists, tables and settings may scroll, and only inside their own region.
