# Bubble skin palettes

Ten colour palettes for the Bubble skin, each with a light and a dark scheme, as data. The owner delegated the choice
(2026-10-02: "about ten palettes that fit great"). Design only: no application code, no device access.
Branch `pilot/palettes-data` (from `pilot/design-bubble-taste`, whose `docs/design/mockups/bubble-taste/` is the approved
mockup these values are built for).

Open `index.html` in a browser (static, no build, no network, works from `file://`): palette picker, light / dark switch,
the three glass opacities, and for the selected palette a home card, pill rows in all three surface styles (fill, gradient,
glass), the state set, a pop-up sheet over a dimmed live page, a media tile, an overview of all ten, and the contrast table.
URL parameters: `p=<id>`, `scheme=light|dark`, `op=min|default|max`.

Shared design rules, so any palette sits in the same skin without layout or meaning changes:
- Neutrals carry a small chroma of the palette's hue (OKLCH), so the glass, wallpaper and pills read as one family.
- The warm light fill (`slider.fill`) stays amber in every palette (a lit lamp is warm whatever the theme), tuned per palette.
- Entity accents (rings) and gradient pairs are harmonised per palette but keep their role (light warm, climate cool, security red family).
- State colours (`success`, `warning`, `danger`) keep the same hue family in every palette; only their lightness is tuned.
- Dark accents are a light tone with dark text on them (Material-style `primary` / `onPrimary`), see "Adjusted values".

## Schema (`schemaVersion: 1`)

A palettes file is `{ schemaVersion: 1, skin: "bubble", defaultPalette, palettes: [...] }`; an exported palette is a single
palette object. A palette is `{ id, name: { he, en }, character, schemes: { light, dark } }`. Each scheme is a **closed set**
(unknown keys are an error, every key is required). Colours are `#rrggbb`; `border`, `glass.layer` and `glass.overlay` also
accept `rgba()` / `#rrggbbaa`.

| Token | Use | Proposed `--sw-*` mapping |
|---|---|---|
| `bg` | page background | `--sw-bg` |
| `surface` / `surface2` | pill / card; sub-button, chip, slider track | `--sw-surface` / `--sw-surface-2` |
| `surfaceElevated` | opaque sheet (no-blur fallback), table, settings | `--sw-surface-solid` |
| `text` / `textMuted` | primary / secondary text | `--sw-text` / `--sw-text-2` (and `-3`) |
| `border` | hairlines | `--sw-border-strong` |
| `accent` / `accentContrast` / `accentText` | buttons, toggles, focus / text on the accent / accent used as text | `--sw-accent` / (white today) / `--sw-accent-text` |
| `glass.tint` + `glass.opacity.{min,default,max}` | the translucent surface colour and its opacity range (the transparency setting moves inside the range) | `--sw-sheet-rgb` + `--sw-sheet-alpha` |
| `glass.layer` | a pill sitting on the glass | `--sw-layer` |
| `glass.overlay` | dims the live page behind a pop-up | `--sw-overlay` |
| `glass.blurPx` | backdrop blur radius | `--sw-glass-blur-sheet` |
| `state.on/off/unavailable/success/warning/danger` | non-text state marks (dots, rings, outlines) | `--sw-toggle-on`, `--sw-success` ... |
| `state.successText/warningText/dangerText` | state as text | `--sw-success-text` ... |
| `entity.light/climate/cover/media/security/camera` | per entity-type ring / accent | NEW `--sw-ent-*` (replaces the hash-assigned `--sw-hue-n` for rings) |
| `entity.icon` | the glyph on an entity ring | `--sw-ring-on-hue` |
| `gradient.pairs` + `gradient.text` | `[start, end]` washes of the gradient surface, and the text on them | `--sw-hue-n` / `--sw-hue-n-mute` |
| `slider.fill` / `fillCool` / `onFill` | warm (lit lamp) and cool (white lamp, cover, volume) fill; label on the fill | `--sw-lit` / `--sw-lit-cool` / `--sw-on-lit` |
| `slider.edge` | a 3 px mark at the fill edge (needed where fill vs track < 3:1) | NEW `--sw-fill-edge` |
| `slider.track` | the unfilled part | `--sw-surface` |
| `wallpaper.stops` + `wallpaper.angle` | 2-5 stops of the wallpaper gradient the glass is designed over | `--sw-canvas` |

How the skin layer and the colour editor use it: load the file (or one exported palette), validate it (schema + contrast,
below), map the tokens to `--sw-*` for `<html data-skin="bubble" data-theme>`. Export = write the single palette object.
A user palette that fails is not applied; the editor shows the failing pairs and the suggestions.

## Contrast method

`validate_palettes.mjs` checks every palette x scheme: 97 pairs light, 93 dark (the edge-mark pairs appear only where
the fill alone is below 3:1).

- WCAG 2.x: sRGB relative luminance, ratio `(L1 + 0.05) / (L2 + 0.05)`. **Text 4.5:1**, **non-text 3:1** (states, rings,
  icons on rings, toggles / accent, slider position).
- Translucent colours are alpha-composited (source-over in sRGB, as the browser paints) onto what is behind them.
  Backdrop blur averages the wallpaper, so the worst case is a large uniform area of a single stop: the validator picks the
  **lightest and the darkest wallpaper stop** and uses the palette's **minimum glass opacity**. For each it builds:
  the glass card (tint over the stop), the pop-up sheet (tint over the overlay-dimmed stop) and the pill layer inside the sheet.
- Pairs: `text` and `textMuted` on bg / surface / surface2 / surfaceElevated and on every glass composite; `accentText` on
  the glass and the opaque surfaces; `text` on every wallpaper stop; `accentContrast` on `accent`; `accent` vs bg / surface;
  every `state.*` mark vs bg / surface / surfaceElevated and the worst glass composite; the three state text tones on the
  surfaces; every entity ring vs bg / surface and `entity.icon` on every ring; `gradient.text` on both ends of every pair;
  `onFill` on both fills; slider position = fill vs track >= 3, **or** the edge mark >= 3 against both fill and track.
- Not computed: text over media artwork (the art varies; the tile keeps the text on a glass panel), intermediate points of a
  gradient (both ends are checked, a linear wash in between stays within them for these pairs), icons other than ring glyphs.

```
node docs/design/palettes/validate_palettes.mjs                 # summary per palette + failures; exit 1 on any failure
node docs/design/palettes/validate_palettes.mjs --all           # every pair
node docs/design/palettes/validate_palettes.mjs --fix-suggest   # nearest passing value per failing token
node docs/design/palettes/validate_palettes.mjs --file my-palette.json [--fix-suggest]
node docs/design/palettes/validate_palettes.mjs --json report.json
node docs/design/palettes/validate_palettes.mjs --emit-preview  # rewrite preview-data.js after editing palettes.json
node docs/design/palettes/shoot.mjs                             # re-take screens/
```

**Validating a custom palette**: export it as a single palette object (or a palettes file) and run with `--file`. The
validator first checks the schema (closed set, formats, `0 < min <= default <= max <= 1`), then all contrast pairs.
`--fix-suggest` walks the failing token's OKLCH lightness up and down (hue and chroma kept) and prints the nearest value
that passes every check in which that token is the foreground. Suggestions are per token: when two related tokens both
fail (for example `accent` and `accentContrast`), apply one and re-run. The module also exports `schemaErrors`,
`checkScheme` and `suggest` (pure functions; only the CLI part uses `node:fs`), so the colour editor can lift the same
rules into the browser.

## Owner decisions (2026-10-02 night) and how the app implements them

Questions 1-5 above are answered; the app (`frontend/src/design/palette.ts`, `system-palette-editor.ts`, backend `services/palettes.py`) does this:

1. **Dark accent**: always a LIGHTER shade than the light scheme's accent. The ten palettes already are (data unchanged). For a custom palette
   `effectiveScheme()` derives it in code: a dark accent that is not at least 1.35:1 lighter than the light accent (and 3:1 against the dark
   `bg` / `surface`) is mixed toward white until it is; the text on it is re-picked for 4.5:1. The editor offers RECOMMENDED swatches for
   every key colour (the accent first; the values the ten ready palettes use) and a free colour picker.
2. **Icon rings** stay the accent colour (`RING_MODE: 'accent'` in `palette.ts`). The alternative stays as a documented FUTURE option:
   set `RING_MODE` to `'pairs'` and the rings take per-entity-type hues from `gradient.pairs` (the `entity.*` tokens remain in every palette
   for it; a unit spec keeps that mode working). With monochrome rings the gradient washes are accent washes: `washShares()` lowers the
   accent share of the wash (`--sw-wash-start` / `--sw-wash-end`, default 40 % / 24 %) and of the lit part (`--sw-wash-lit`, default 70 %)
   per palette and scheme until text and muted text read at 4.5:1 on the wash and the on-fill text on the lit part (`unit-palettes.spec.ts`
   asserts it for every palette and both schemes).
3. **All ten palettes** are offered (plus `default`, the skin's own colours).
4. **A failing custom palette only WARNS**: the editor lists the worst pairs in Hebrew and offers "תקן אוטומטית" (`autoFixPalette`: failing
   foreground colours move to the nearest passing value, backgrounds stay) and saving stays allowed. The backend accepts it (no 422 for
   contrast) and still refuses a structurally invalid palette; the app falls back to the previous valid palette only for a structurally
   invalid one.
5. **Import / export** of palettes: not now.
6. **Who chooses**: only the installation's system administrator (`system.configure`, the settings gate) sets the palette, for everyone.
   There is no personal palette override: the row is not shown on "ההעדפה שלי", `lookOf('palette')` never reads a personal value and
   `/me/prefs` drops a `palette` it is given. The other look dials keep their personal overrides.

## Adding a palette is a data-only change

1. Append the palette object to `palettes.json` here (same schema as the others; `id` lower-case kebab, `name.he` / `name.en`).
2. `node validate_palettes.mjs` must pass (every contrast pair), then `--emit-preview` to refresh `preview-data.js`.
3. Copy the file to `frontend/src/design/palettes.json` and to `smplwise_vms/backend/smplwise/palettes.json` (a unit spec and a backend test
   keep the three identical; the file name list of the dial, its Hebrew labels and the backend's accepted ids are all read from it).
4. Bump the release notes. Nothing else.

No component, token table, CSS or id list changes: the loader maps any valid palette to `--sw-*` custom properties, the look dial's
choices (`LOOK_DIALS.palette`) and the backend's `BUILTIN_IDS` are generated from the file.
