# ADR019-FAMILY45-2520

ADR-019 (`docs/architecture/ADR-019-error-envelope-and-request-strictness.md`), decision D1 (L2, one field-error envelope),
"Step 1..n" for **family 4 (tickets main-app routes, messaging accounts, notifications, notify)** and **family 5 (access control /
WisKey)**, exactly as the ADR's order table lists them, following the way families 2 and 3 were done
(`docs/changes/ADR019-FAMILY2-2500.md`, `docs/changes/ADR019-FAMILY3-2510.md`). Family 6 is not started. The L14 part (request-model
strictness) is another row and is not touched.

Branch `pilot/ADR019-FAMILY45-2520` from `origin/main` = v2.51.0 (3d71fb183). Pixel-neutral: no text, placement or style changes;
statuses, envelope `code`s and `user_message`s are unchanged.

## What changed

### Family 4 - `fields` as objects -> `problems`, then `fields` -> names (one step, ADR-019 D1)

The legacy form lived under the same key (`details.fields: [{field, code}]`), so - as D1 prescribes - the objects moved to
`details.problems` and `details.fields` became their names in the same row in which every reader of the family moved to the shared
reader (`problemsOf`, which reads both forms). The objects are unchanged field by field (`problems` = the old `fields`).

| Module | Before | Now |
|---|---|---|
| `routers/_tickets_common.py` `invalid` / `invalid_fields` (every tickets router: rules, catalogue / SLA, messages, table, visits, ...) | `details.fields: [{field, code}]` | `field_error(..., problems=[{field, code}])` -> `fields` (names) + `problems` |
| `services/tickets/service.py` `invalid`, `cost_error` (422 not in `COST_MESSAGES`); `contacts.py`, `intake.py`, `rfq.py`, `staff_links.py` `invalid`; `external.py` (6), `phone_verify.py` (2); `routers/tickets.py` (delete `confirm_number`), `tickets_map.py`, `tickets_table.py` | same | same |
| `routers/tickets_admin_locations.py` 409 `location_name_taken` | `fields: [{field: name, code: duplicate}]` | `fields: ["name"]`, `problems: [{name, duplicate}]` |
| `services/tickets/visits.py` `VisitRefused(422, ..., fields=[...])` (7, internal) -> `routers/tickets_visits._err` | the router answered the objects | `VisitRefused(..., problems=[...])`; the router answers `invalid_fields(problems)` |
| `routers/messaging_accounts.py` `_problems` (save, targets, pacing, policy, self window) | `details.fields: [{field, code}]` | `field_error("ערך לא תקין.", problems=...)` |
| `services/tickets/service.py` `cost_error` (a known cost code with `exc.field`) | `details.field` (+ extras) | + `fields: [field]` (legacy `field` kept) |
| `routers/tickets_admin_departments.py` 409 `department_key_taken` (3) | `details.key` (the key's VALUE) | + `fields: ["key"]` (legacy `key` kept) |
| `routers/tickets_admin_settings.py` 403 `local_only`, `services/tickets/contacts.py` 409 `module_key_missing` | `details.field` | + `fields` (legacy `field` kept) |
| `routers/notifications.py` (6: `If-Match`, `category`, `before`, `to`, `status`, `since`), `routers/notify_whatsapp.py` (`confirm`) | `details.field` | `field_error(..., legacy={"field"})` |
| `routers/notifications.py` settings / email / policy, `routers/notify_whatsapp.py` config: the service refusals (`SettingsInvalid`, `PolicyInvalid`, `ConfigInvalid`, built at run time - the scan reads them as `dynamic`) | `details.field` (+ `min`, `max`, `allowed`, ...) | new `errors.named_field_error()`: + `fields: [field]` when the details name one field; every other key kept |

In-process readers of the objects (backend): `services/tickets/rule_engine.py` (the refused rule's audit `fields`) reads names (and
still objects); `services/partner/api_app.py` builds its own `{code, fields: [{field, code}]}` answer from `problems` (the partner
API's answer is unchanged).

**Public app (out of scope, D1).** The public pages' vocabulary is unchanged: `PublicError`, and the refusal classes the public
routes answer as they are - `VendorRefused` (RFQ vendor, terms, postpone), `ActionRefused` (handler actions, visits by link),

counted them in the tickets / access families. `scripts/error_contract_inventory.py` now counts them with the public app
(`PUBLIC_VOCABULARY`, `PUBLIC_VOCABULARY_AT`; `tickets/attachments.Refused` is main-app and stays). `frontend/src/public-ticket/*`
is untouched.

Legacy-key removal (Step 1 (d)) is NOT part of this row: the legacy `field`, `key`, `code` and `errors` keys stay; one release later,
after the inventory shows no reader of them. (`fields` as objects and the profile draft's `{path, code}` are already gone - D1's
one-step rule for a legacy form under the same key; release-notes line: "tickets / messaging accounts / access profile 422s:
`details.fields` lists names, the `{field, code}` entries are in `details.problems`".)

## Open questions (built to the recommendation)

1. Family 4's `fields` turned from objects into names in this row (D1's one-step rule), so a client that still read the objects
   would see names. Every reader is the web UI shipped in the same image (moved here) and two in-process readers (moved here); the
   public pages and the partner API keep their own `{field, code}` answers. Recommendation: a) keep it in 2.52 with the
   release-notes line above; b) hold `fields` as objects one more release (then the shared reader is the only gain).
2. `services/intercom_messaging.py` (`message_settings_invalid`) is inventory family `intercom` (ADR order 8), but it is the access
   control messaging settings screen, the same `{path, code}` issue list as template-send / WA-queue. Recommendation: a) keep it in
   this row (one screen, one shape); b) move it back to family 8.
3. The 403 `local_only` (tickets public-address settings) also gained `fields` - D1 names "422 and the few 400 / 409". Recommendation:
   a) keep (additive, the refusal is about that field); b) revert to `field` only.
4. `routers/intercom_calls.py:104` (`details.field`, family `intercom`) is the one legacy site left in the intercom family.
   Recommendation: a) family 8; b) a follow-up row now.
