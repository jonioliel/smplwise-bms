# T068-SOAK-2406 - long soak harness and the overnight run

Branch `chore/T068-SOAK-2406` from `release/2405-train` @ `eadc5b080`. Card T068 (AT135 / AT136), budget source
`docs/operations/RESOURCE_BUDGET.md`; the 10-minute device-free soak (`SOAK_LOCAL.md`) stays as it is.

## Method

- `smplwise_vms/backend/tests/soak/soak_long.py` (harness) + `soak_long_backend.py` (the backend process). The backend runs
  in its own process (`create_app` + uvicorn, asyncio + h11, fresh data dir `<run>/data`), so its RSS / CPU / fds are its own.
- Fakes on 127.0.0.1: NVR (soak_local's: alertStream ~6 alerts/s on 8 channels, search, paced download; restart every 30 min,
  down 15 s), Home Assistant with 600 entities and 20 `state_changed`/s plus the fake WisKey (`tests/fake_wiskey.py`) on the
  same socket (restart every 45 min, down 10 s), go2rtc (stream registry + `/api/ws` media, ~80 KB/s per viewer; restart
  every 60 min, down 10 s).
- Load: 4 operators (screen mix, 2-6 s think time), acker (10 s), exporter (10-min export every 3 min, keeps 3), 3 event
  WebSockets reconnecting every 5 min, 4 live viewers opening a camera for 20-90 s then the next (session churn).
- Sample every 60 s into `<run>/samples.csv`: backend RSS / private / CPU % / threads / fds / Python objects, DB and WAL
  bytes, event-loop lag p50/p95/p99/max (0.25 s sleep monitor in the backend loop), WebSockets open by kind, live sessions,
  event subscribers, API p50/p95/max of the interval, errors (5xx, unexpected 4xx, client exceptions, backend log errors,
  `database is locked`, write-lock busy), feed state, fake counters, host load / available memory. `summary.json` at the end.
- Guards: `scripts/soak/t068_long_soak.sh` runs it under `nice -n 19`, `ionice -c3`, `taskset -c 14,15`, `prlimit --as`
  3 GB per process, `MALLOC_ARENA_MAX=2`; the harness pauses client load while host MemAvailable < 800 MB and stops on
  backend RSS > 1200 MB (`rss_cap`). `systemd-run --user --scope` was not used: on the runner the user manager only lives
  while a login session exists (Linger=no), so a user scope would be killed when the gate's session ends. Command lines
  contain no `pytest` / `uvicorn` / `vite`, so `cleanup_orphans.sh` (4 h hard age on those patterns) leaves the run alone;
  `~/soak` is on `runner_cleanup.sh`'s never-touched list.

### Root cause of the write-lock failure (fixed on `fix/T068-INGEST-LOCK-2406`)

`events_ingest._write` is one short transaction per alert (no batching), but `store_alert`'s merge lookup - "the open row of
this camera / kind last seen within `DEDUP_WINDOW_S`" - filtered on `COALESCE(ended_at, occurred_at)` and
`COALESCE(camera_id, '')`, which no index covered: `EXPLAIN QUERY PLAN` = `SCAN events` + temp B-tree. Every alert that
starts a new burst therefore scanned the whole events table under the write lock, linear in its size (workstation, warm
cache: 7.8 ms at 2k rows, 59 ms at 50k, 414 ms at 200k). With the soak's table growing to 548 MB and the backend under
`ionice -c3` next to an L gate, a few of those scans took 17 s; the rising CPU (18.5 % -> 68.2 % while the host went quiet)
fits the same linear cost (not separately verified). Fix: migration 0207, a partial index
`idx_events_alert_open (type, COALESCE(camera_id, ''), COALESCE(ended_at, occurred_at)) WHERE source = 'alertstream' AND
state = 'active'`; the active lookup now ranges over the rows seen inside the window (`ORDER BY +occurred_at` so the time
index is not chosen for the sort), and the inactive lookup carries the implied last-seen term so it is bounded the same way
(2.3 ms at 200k rows, same plan at any size). Results and order are unchanged. Tests: `tests/test_ingest_lock_bound.py`.

Fix tests (workstation, Windows 11, Python 3.12, 2026-11-07): `tests/test_ingest_lock_bound.py` 6 PASS; 4 of them FAIL
on the pre-fix code (plan, work bound x2, migration); the backlog fairness test passes on both (30k rows scan in < 1 s on
the workstation - it guards the per-alert transaction shape, not the scan). Related suites run together (backpressure,
db_* gate / locking / contention / lock storm / pool / io guard / template, events, events_cache, events_cache_perf,
frigate_events, multi_nvr, multi_nvr_identity, migrations, migrations_263_upgrade, rules, soak_long, soak_sampler, plus the
new file): 236 collected, 232 passed, 4 skipped (opt-in load tests), 0 failed. The long soak with the fix: NOT_RUN.

### Other findings

- `label registry listing failed; keeping the previous label mirror` x96: a harness gap - the soak's fake HA did not answer
  `config/label_registry/list` (unknown_command on every registry refresh). Fixed in `soak_long.py` (empty label list).
  The product's warning stays as it is (a real HA without labels is an old core; one line per refresh).
- events cache hit rate 0.014: by design, not a defect. 82 % of the misses are `stale` (the key was cached at an older
  `cache_versions` version): at ~6 alerts/s plus acks the events counter moves between almost every two reads, and a
  cached window is never served for an older version (the 2026-09-29 note already says the list's hit rate stays low under
  ingest). The rest are first reads of per-camera / per-day keys inside the 5 s TTL. No change made.
- `notify_sources.py` has a similar open-row lookup (`type = 'storage'`, no camera); it now has `type` equality on the new
  index, but walks every open storage row - small in practice, noted only.
