# ADR019-FAMILY678-2520

ADR-019 (`docs/architecture/ADR-019-error-envelope-and-request-strictness.md`), decision D1 (L2, one field-error envelope),
"Step 1..n" for **families 6, 7 and 8** of the ADR's order table. Families 4-5 (tickets, messaging, notifications, access control /
WisKey) are the parallel row `pilot/ADR019-FAMILY45-2520` and are not touched here. The L14 part (request-model strictness) is
another row.

Branch `pilot/ADR019-FAMILY678-2520` from `origin/main` 3d71fb183 (v2.51.0). Pixel-neutral: no text, placement or style changes;
statuses, envelope `code`s and `user_message`s are unchanged; every change under `details` is additive (the legacy key is still
sent - Step 1 (d) removes it one release later, after the inventory shows no reader).

## What changed

### Family 6 - automations, scenarios, schedules, blueprints

| Module | Before | Now (legacy key still sent) |
|---|---|---|
| `services/automation_ops.py`, `services/schedule_ops.py` `problem_error()` (every refused save / preview of an automation, script, scene or schedule) | `details.errors: [{path, code, message}]` (+ `path` for a promoted code) | `field_error(..., problems=issue_problems(errors), legacy={"errors"}, extra={"path"})` |
| `services/scenarios.py` `_validation()` (9 call sites), `routers/scenarios.py` simulation `overrides` (2) | `details.errors` | the same, via `issue_problems` (`fields: ["overrides"]` for the simulation values) |
| `routers/automation_blueprints.py` `_problems()` (per-parameter refusals `[{param, code, message}]`) | `details.errors` | `fields` / `problems` name the body's `params.<name>` |
| `services/scenario_settings.py` (unknown / invalid setting) | `details.key` | `field_error([key], code="invalid_setting", legacy={"key"})` |

**`errors.issue_problems(issues, *, key="path", prefix="")`** (new, next to `field_error`): a domain issue list as D1 problems -
`field` = the issue's path, `code` / `message` as they were. An issue with an EMPTY path is about the submitted item as a whole; D1
needs a field in every problem, so it is `body` (`errors.WHOLE_BODY`, the ADR's own word for the request as a whole) - the web UI maps
it back to the empty path. Paths stay relative to the item (`triggers.0`, `slots.1.start`), as family 3 kept its legacy names
(open question 2).

**Forwarded `(status, payload)` replies** (`routers/automations.py`, `routers/schedules.py`, `routers/automation_blueprints.py`
`_reply`, plus `routers/cast.py` / `routers/multimedia.py` of family 8): checked - every status these services return as a tuple is
a success (200 / 201 / 202, including the stored idempotent replies); every refusal is raised as `ApiError` and answered by the one
handler. A static test pins this.

### Family 7 - electricity and water billing

The server already answered `fields` as NAMES everywhere (the "map" form lived only in the demo store,
`api/electricity-billing-mock.ts`). Changed:

| Module | Before | Now |
|---|---|---|
| `services/energy_billing.py` `tou_error()` (refused time-of-use definition, electricity and water) | `errors: [{code, path, message}]`, `fields: ["definition.<path>"]` | + `problems: [{field: "definition.<path>", code}]` |
| `services/energy_billing.py` `formula_error()` (refused account formula, electricity and water) | `errors: [{code, message, pos}]` | + `fields: ["formula"]`, `problems: [{field, code}]`; the two preset routes name `preset` |

These problems carry no `message`: the text IS the envelope's `user_message` (one issue), and `elecFieldErrors()` treats a problem
with a message as a message under a form field - a definition / formula issue must stay the general line it is today.

Screens: `elecFieldErrors()` reads `problemsOf` (per-field messages), `elecCustomerNumberError()` reads `fieldsOf`, the tariff
editor's error path (`elec-settings.ts`) reads `problemsOf` (`definition.<path>`, the legacy `errors[0].path` before), the meter
readings dialog and the water customers page read `fieldsOf`. The demo store answers `fields` as names + `problems` with the
message instead of the map, and the tariff refusal with `problems` - the same words land under the same fields.

extras. The media demo store (`api/media-players-mock.ts`) answers the same `fields`. No screen reads `not_groupable` details.

**Left:** `services/intercom_messaging.py` (the access-messaging settings issue list, inventory family `intercom`) - the family-4/5 row

## Open questions - answered by the lead (Q1 = a, Q2 = a, Q3 = a, Q4 = a); kept for the record

1. `services/media_groups.py` `not_groupable` names a device key value, not a field. Decided (a): done on this branch - `fields`
   names the body field per call site, `key` stays as an endpoint extra.
2. The empty issue path becomes `body` in `problems`. (a) Recommendation: keep `body` (the ADR's word for the request as a whole;
   `issuesOf` maps it back); (b) use the item kind (`automation`, `schedule`); (c) leave such issues out of `problems`.
3. Billing definition / formula problems carry no `message` (it is the envelope's message). (a) Recommendation: keep it so - a
   message would make `elecFieldErrors` show it under a field that the form does not have; (b) add the message and filter the
   screen reader by known form fields.
4. The ratchet JSON is new in this row while the family-4/5 row runs in parallel. (a) Recommendation: merge family 4/5 first, then
   this row, and run `--write-ratchet` once on the train; (b) either order, regenerate on the train.
