# ADR019-STEP0-2500

ADR-019 (`docs/architecture/ADR-019-error-envelope-and-request-strictness.md`), decision D1 (L2, one field-error envelope):
"Step 0 - contract and reader" items 1-4, and "Step 1" for family 1 (the `ServiceInvalid` adopters: calendar, transit, notices,
emergency, maintenance, temperature, insights, generator). The L14 part (`extra="forbid"`, the observing request model) is another
row (ADR019-L14-OBSERVE-2500) and is not touched here.

Branch `pilot/ADR019-STEP0-2500` from `origin/main` (d6f09395e, v2.48.0). Pixel-neutral: no text, placement or style changes; the
top-level envelope, statuses and envelope `code`s are unchanged; every change under `details` is additive.

## Step 0

1. **Contract models** - `smplwise/wire/errors.py`: `ErrorEnvelope`, `FieldErrorDetails`, `FieldProblem` (documentation and type
   generation only; the handlers keep building dicts). `scripts/gen_wire_types.py` learned a short `NON_ROUTE` list (file -> module,
   tuple of models) and writes `frontend/src/api/generated/wire-errors.ts` (no route map); `--check` covers it. `ApiErrorBody` in
   `frontend/src/api/client.ts` is now `type ApiErrorBody = ErrorEnvelope` (same five keys, `details: Record<string, unknown>`).
2. **`errors.field_error(message, fields, *, problems=None, code="validation", status=422, legacy=None, extra=None)`** - an `ApiError`
   with `details.fields` (names, each once; the fields of `problems` are added in their order) and `details.problems`
   (`{field, code, message?}`) when given. `legacy` is the family's pre-migration key (`{"field": ...}`), `extra` the endpoint's own
   details (`message_en`, limits); neither may carry `fields` / `problems` (ValueError). `extra` is an addition to the ADR's
   signature so the endpoint extras (not part of the decision) stay apart from the legacy key that Step 1 (d) removes.
   `ServiceInvalid`: new class attribute `field_code` (the per-field reason of a class whose `code` says what is wrong with the
   field); `field_problems()`; `api_details()` adds `problems` when `field_code` is set; `to_api_error()` takes `code=`, `legacy=`,
   `extra=` (the keys of `api_details()` win). The emergency and maintenance `Invalid` classes set `field_code = code`.
3. **Frontend reader** - `fieldsOf(err): string[]` and `problemsOf(err): FieldProblem[]` in `frontend/src/api/client.ts`: the canonical
   `fields` / `problems` first; without them every legacy form (`field`, `key`, `fields` as objects `{field, code}` or as a map
   field -> message, an `errors` list with `path` or `loc`). A form that only names fields gives no problems.
4. **Global handler** - `errors.validation_payload()` (the `RequestValidationError` handler) adds `fields` and `problems`
   (`{field, code: <pydantic type>, message: <the Hebrew constraint text>}`) derived from the same list; `errors` stays.

The inventory (`scripts/error_contract_inventory.py`) recognises `field_error(...)` (canonical `fields`, plus the `legacy` / `extra`
keys), so the family-1 sites count as canonical while their legacy key rides along.
