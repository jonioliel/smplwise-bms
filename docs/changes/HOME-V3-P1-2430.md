# HOME-V3-P1-2430 - home interface mockup v3, phase 1: security and intercom

Branch `pilot/HOME-V3-P1-2430` from `main` a5618fad6 (v2.42.1). The owner approved the round-27 mockup v3 of the home interface
(`private/design-system-2026-10-27/round27/home-full-v3/`, 2026-11-11) and chose to build it in three phases; this is phase 1 (the
security / intercom rows of the mockup's inventory table). Builds on HOME-SIMPLE-2420 and HOME-SIMPLE-2421 (read those first). No version
bump, no CHANGELOG edit, API inventory not regenerated (the release bump does it). Nothing in `private/`, `secrets/`, the lab,
`frontend/src/map/` or `management/*.json` was touched.

## What changed

### 0. The extension point (so phases 2 and 3 merge small)

* `frontend/src/home/home-ext.ts`: a screen registry. Each v3 screen is its own file and calls `registerScreen(host => ({ id, names,
  render, enter?, leave?, ovl?, acts?, back?, navCur? }))`; the host is the `sw-home` element itself (its shared pieces - head, seg,
  pager, empty, toast, href, data, overlay - are no longer `private`). `sw-home.ts` only wires the registry in: route names, the
  delegated click handler (a module's `acts` are used when sw-home has no `a_<name>`), an `{ type: 'ext', mod }` overlay, the strip's
  back target, the nav's current item, `enter` / `leave` on route changes.
* `frontend/src/home/more-registry.ts`: the "עוד" hub's tiles (`registerMoreTile({ id, order, href, label, icon, visible, line, warm? })`).
  Phase 1 uses `order` 10-40; phases 2 / 3 are asked to use 50-90 / 100+.
* `frontend/src/home/home-v3-p1.ts`: imports the phase-1 files (one import line in sw-home.ts). Phases 2 / 3 add their own index file.
* `frontend/src/home/home-styles-v3.ts`: the WHOLE `v3.css` of the mockup, ported once by the same mechanical rules as `home-styles.ts`
  (`scripts/home_port_v3_css.py`: `--sw-*` -> `--hs-*`, `#ovl` -> `.ovl`, `[data-theme="light"]` -> `:host([data-hs-scheme="light"])`,
  demo panel dropped), so phases 2 / 3 need no style port of their own. Product-only additions are in `home-styles-extra.ts`.
* `home-icons.ts`: the 30 icons the mockup v3 added (same set and grid).
* Backend: `HOME_READ_ONLY_EXACT / _PREFIXES` (GET / HEAD only) and `HOME_FLAG_ROUTES` (routes reachable by a home-only person only with
  a per-person flag) next to the existing allowlist; each phase appends its own block.

### 1. The "עוד" hub (sixth nav item, ninth home category)

`#/home/more` (`home-more.ts`): the tiles of the capabilities this person has, with a live line (paged: 18 per page, 12 on a phone).
The nav gets "עוד" between "פעיל עכשיו" and "התראות" (on a phone "פעיל עכשיו" shortens to "פעיל", the mockup's rule); the home screen
(not a room) gets an "עוד" chip as its ninth category, with "N חדשים" when a tile waits (missed calls). The hub's children go back to the
hub and mark "עוד" in the nav. Not shown on a locked wall panel. Phase 1 tiles: הקלטות, יומן הבית, אינטרקום, אזעקה - each only when
its category / permission is on (below); with none, the hub says so.

### 2. Recordings (`#/home/playback/<camera>`, `home-recordings.ts`)

One camera, one day, a simple timeline, "מה קרה כאן" (the camera's events of that day, paged) and "חזרה לחי".

* Owner decisions: the timeline runs LEFT TO RIGHT (`<div class="tl" dir="ltr">`, the axis 00:00 .. 24:00), the picture is never
  mirrored, and a resident may watch EVERYTHING stored: the day stepper goes back without a cap (היום / אתמול / שלשום / a date); the only
  limits are `video.playback` per camera (checked by every route) and what the recorder keeps.
* Routes (existing): `GET /cameras/{id}/recordings?date=` (the segments, drawn on the axis), `GET /cameras/{id}/events?date=`,
  `POST /playback/sessions` + `/seek` + `DELETE` (the session closes on pause, on "חזרה לחי" and when the screen is left; the page's
  beacon closes it on unload), played by the existing `sw-live-player` in MSE.
* Offered when the cameras category is on, a camera exists and the person holds `video.playback`: a "הקלטות" button on the cameras
  screen and "הקלטות של המצלמה" at the foot of the full-screen camera, as the mockup.
* Errors are family words (`playbackError`): no recording at that time / no permission / too many viewers / not available now.
* **Sub stream - NOT for recordings (open question 1).** The live pictures of the home interface stay on the light stream as before; a
  recording is played from the recorder's recorded track (`cameras.main_track`, the only track the playback service opens). Playing the
  sub track would need the playback service to open `sub_track` and the recording search to search it, and the lab has not shown that
  the recorder records the sub stream (AGENTS.md: capability discovery, no track formula). Not changed here.

### 3. The home diary (`#/home/events`, `home-diary.ts`)

The last 7 days, newest first, paged (8 / 5 on a phone), filter הכל / דלתות / מצלמות: people and movement at the cameras, a door that
opened, the doorbell (from the call log). Technical events (system, storage, coverage, offline, tamper) stay in the full interface.
"צפה בהקלטה" opens the recording 5 seconds before the event (`playback/<camera>@<epoch>`) when the person may play it. Routes:
`GET /events` (read-only for a home-only person) and `GET /intercom/calls`. Shown with `events.read`, or with the doors category +
`access.read` (calls only). The mockup's "אזעקה" filter is not built (no alarm event kind in the events log; the alarm's own changes are
on its screen).

### 4. Intercom (`#/home/intercom/<calls|guests|people>`, `home-intercom.ts`)

Shown with the doors category and `access.read`. The home screen's intercom chip now opens this screen.

* **Calls**: the call log (`GET /intercom/calls`, 40 newest, paged 8 / 4) - station, time, who opened / answered / missed - plus "דבר עם
  הכניסה" where the station drawer's talk is offered (the 2.42.0 path). No picture per call: the call log keeps no frames.
* **Guests** (owner: only people the home administrator marked): the tab exists only when (a) the administrator marked the person
  (`guests`, below), (b) the person holds `access.visitor.invite`, and (c) the visitor invitations are on for the installation
  (`access.visitors` + external grants; **left off by default as found** - the global default is not changed). It lists the person's own
  live invitations; "הזמן אורח" opens the mockup's short sheet (name, door, today / tomorrow, from / to hour) **plus the guest's phone
  number** - the engine needs it, because the door code goes to the guest's phone. Saving is the existing `POST /access/visitors` (inside
  the envelope the host's own act approves it; outside it waits for a second person - shown as "מחכה לאישור של מנהל הבית"). The doors
  offered are `GET /home/guest-doors` (new, below).
* **The code is never shown** (deviation from the mockup's "show code" sheet, required by the visitor engine's design: the host never
  sees a door code). That sheet became the invitation's detail: its state, doors and hours, and the number confirmation the engine asks
  for before any code exists ("שלח לאורח קוד אימות" -> `POST .../verify/send`, then the code the guest reads -> `.../verify/check`).
  Cancel asks first ("הקוד יפסיק לעבוד מיד") -> `DELETE /access/visitors/{id}`. The mockup's "קבוע" (weekly) option is not offered:
  an invitation is one window of at most the installation's maximum hours.
* **Who can come in** (view only, `access.people.read`): `GET /intercom/people` (names, validity, how many doors; never phones, cards or
  codes - the route's own projection). The mockup's "נכנס עם: קוד / תג / פנים" cannot be shown: the people route deliberately carries no
  credential data, so the column says how many doors the person may open. "Adding people, codes and tags is done by the home
  administrator in the full interface."

### 5. Alarm (`#/home/security`, `home-alarm.ts`, replaces the 2.42.0 list)

Drawn as the mockup: the state word in a large pane (מנוטרלת / דרוכה: מלאה / דרוכה: בבית / אזעקה פעילה), the open sensors line, the
arm buttons (דריכה מלאה / דריכה: בבית / דריכת לילה - those the panel offers) or "נטרול", and the doors / windows / detectors list
(paged). **Arming stays one tap + one confirmation sheet** (the mockup's texts, with the open sensors counted); a panel that asks for a
code on arming gets the code pad instead; disarming asks for the code the panel needs (the existing code pad) or a confirmation.
**Personal alarm code**: "הקוד האישי שלי" -> the current code (or, for a first code, the panel's code - the existing rule of
`PUT /alarm/me/pin`), the new code, the new code again (a mismatch starts over) -> `PUT /alarm/me/pin`. Several panels: a picker. The
2.42.0 spec's arm test now clicks the new button (`almArm`); its flow (tap + confirmation through the alarm route) is unchanged.

### 6. Owner decision 16b: the administrator's room wallpaper for everyone

User management > "ממשק ביתי" > "הגדרות התקנה" > "רקע לחדר לכולם" (shown while the installation offers wallpapers): a room picker,
the 8 gallery backgrounds or none, and (with pictures on) a picture for the room. **Choice of precedence: a person's own wallpaper wins
over the administrator's, EXCEPT on a wall panel (kiosk), where the administrator's always shows.** Server: `home.room_wallpapers`
(settings row) + a shared picture = a `home_room_image` row with user_id `*` (same sanitizer, same 2 MB limit and body-limit rule,
re-encoded, EXIF dropped). Routes (`routers/home_v3.py`, rbac.assign, audited without the picture): `GET /home/room-wallpapers`,
`PUT /home/room-wallpapers/{room}` `{value: "g:<name>" | ""}`, `PUT | DELETE /home/room-wallpapers/{room}/image`; the picture is
served to anyone signed in by `GET /home/room-wallpapers/{room}/image` (it is the room's background). Everyone reads the applied set in
`GET /home/interface` (`room_wallpapers`; a picture only while pictures are on and it exists; unknown gallery names dropped).

### 7. The guest mark per person (owner decision)

User management > "ממשק ביתי" > a person > "רשאי להזמין אורחים" (`PUT /home/policies/{user}` `{guests}`, audited before / after).
It is never a grant: the page says when the person lacks the visitor-invite permission ("הסימון לבדו לא מספיק", from `can_invite` in
`GET /home/policies`). "Switch user" inside the home system stays as built in 2.42.1.

## Server-side gate (home-only people)

| Route | Home-only person |
|---|---|
| `/cameras/{id}/recordings`, `/recordings/days`, `/cameras/{id}/events` | allowed (already under `/cameras/`) |
| `/playback/sessions`, `/playback/sessions/...` (seek, close, the relay socket) | allowed (new) |
| `/alarm/me`, `/alarm/me/pin` | allowed (new) |
| `/events`, `/events/...` | GET / HEAD only (new): acknowledging, groups and windows stay refused |
| `/intercom/people` | GET / HEAD only (new): creating a person stays refused; `/intercom/people/{id}/editor` etc. stay refused |
| `/access/visitors`, `/access/visitors/{id}`, `.../verify/*` | only with the person's `guests` mark (new) |
| `/access/visitors/settings`, `/revoke-all`, `/entrances/...` | always refused |

Every allowed route still checks its own permission; the gate only restricts. `enforce()` now receives the request method from
`auth._principal` (a WebSocket has none and counts as GET).

## Migration and rollback

Additive migration `0213_home_v3_p1.sql`: `home_interface_policy.guests INTEGER NOT NULL DEFAULT 0` (nobody marked after the upgrade).
The room wallpapers need no table (a settings row + `home_room_image` rows with user_id `*`). Rollback: the previous version ignores the
column, the setting and the shared rows; the gate goes back to the 2.42.1 list (home-only people lose recordings, the diary, the people
list, the personal code and guests again - safe direction).
