# W031-295 - admission review of every signed direct command to the WisKey bridge

WisKey item W-031. Base: `pilot/WK4ADOPT-295` @ `80e3eed68` (the combined candidate). Branch: `pilot/W031-295`.

Question: does every signed command that Arx sends to WisKey on the direct transport (`services/wiskey_direct_join.py`: one
authenticated `direct/connect` socket, envelope `wiskey-bridge-command.v1`, or `wiskey-peer-query.v1` for `PEER_QUERY_COMMANDS`;
plus the W10 media links of `services/wiskey_media_bridge.py`) map identity, role and scope to an Arx admission decision - who may send
which command, under which role and scope, with person / permission revision checks? Constraint: no new gate, no new wire field.

Note on the file names in the brief: there is no `bridge_command_auth.py` in this tree. The signing and reply verification it would
hold live in `services/wiskey_media_bridge.py` (`BridgeSigner.proof`, `DirectLink.signed_body` / `call_command`, `open_reply`,
`verify_command_result`); the two ports are `services/wiskey_command_port.py` and `services/wiskey_capture_port.py`.

Status: reviewed by reading the code and by unit tests against the in-memory fakes only. Nothing was run against a WisKey, Home
Assistant, a station or a door.

## Observations (not changed - recorded, not silently resolved)

- O-1 Templates: when a production caller of `TemplateSender` is wired, it must bring its own person admission (who may message
  which person); the sender layer has none today. Adding one here would be a new gate without a caller, so it is left to the item that
  wires the route.
- O-2 `LiveResolveTransport` does not re-check `wiskey_peer.go_live_permitted()` the way `LiveRegistryTransport` checks its permit.
  Both permits are True in this build and both reads carry no person actor; parity only.
- O-3 `ListenLease` (routers/intercom_listen.py) has the same `access.call`-only shape G3 fixed for talk. Listening sends nothing to
  WisKey yet (`downlink_pending`); align it when the downlink contract lands.
- O-4 Feature `authority_revision` is caller-attested (`FeatureAdapters.prepare` does not compare it with `permission_revision`); the
  emergency resolver reads it fresh, and the snapshot's permissions are always resolved now. Binding it generally would break the
  automation lineage rule (`grant_revision == authority_revision`), so it is not changed here.
- O-5 The native people-write re-decision checks `access.people.manage` only; the route gate (which always runs first on the same
  request) carries the sensitive level and the per-command permission set. Defence in depth, not a gap.
