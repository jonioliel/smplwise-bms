# FIX-MH01-2560 - the room's area field and the link-dropping writes run the building RemapGuard

Row FIX-MH01-2560 (2.56, high, security). Finding MH-01 of `docs/review/DEEP-REVIEW-2560-MAPS-HOME.md`
(branch `review/DEEP-2560-MAPS-HOME`). Base: `origin/release/2560-train` at `3739e3ded`.

## The finding (confirmed at the base before the fix)

A plan room's area link (`spatial_zones.ha_area_id`) is the first source `building_scope.area_targets()` reads for an area's
building. `POST /plan/area-links` ran the round-14 `RemapGuard`; `PATCH /zones/{id}` with `area_id` (the plan editor's own room
field) wrote the same column with only `placement.edit` on the room's floor. A floor editor of building A could link building B's
area to a room on his floor and pull B's devices into the reach of A's holders (multi-building on, reach `map_and_mapping`), and
open sockets were not re-scoped. Reproduced at the base by the new test: `PATCH` answered 200 where `/plan/area-links` answers 403.

## Every writer of the area -> building resolution (inventory)

| Writer | Route | Before | Now |
|---|---|---|---|
| room link `spatial_zones.ha_area_id` | `POST /plan/area-links` | RemapGuard | unchanged |
| room link `spatial_zones.ha_area_id` | `PATCH /zones/{id}` (`area_id`) | **no guard** | RemapGuard (`placement.edit`) - MH-01 |
| room deleted with its link | `DELETE /zones/{id}` (plain and `with_unshare`) | no guard, no re-scope | RemapGuard (`placement.edit`) |
| auto rooms replaced | `POST /floors/{id}/zones/accept` `replace_auto` | no guard, no re-scope | RemapGuard (`placement.edit`) |
| floor deleted (its links and rooms stop counting) | `DELETE /floors/{id}` | no guard, no re-scope | RemapGuard (`site.content.configure`), checked before any file is removed |
| building deleted (its area -> building rows stop counting) | `DELETE /buildings/{id}` | no guard, no re-scope | RemapGuard (`site.content.configure`) |
| layer 1 / 2 rows | `PUT /floors/{id}/home-link` | RemapGuard | unchanged |
| layer 1 / 2 / area -> building rows | home mapping apply / restore | RemapGuard | unchanged |
| floor moved to another building | `POST /floors/{id}/move` | content edit on BOTH buildings + re-scope | unchanged (stricter than the guard) |
| new rooms (`POST /floors/{id}/zones`, accept, share conversion) | - | never carry a link | n/a |
| `PATCH /floors/{id}` | - | no mapping column (`floors.ha_area_id` is not read by `area_targets`) | n/a |
| background auto-insert (`services/mapping_auto.py`) | system, no principal | inserts only new rows, never moves a placed one | n/a |
| backup restore | `backup.manage` installation-wide | - | n/a |

The refusal is the guard's own: `rbac.require` -> audited 403 `forbidden` (the same code and audit as `/plan/area-links`), the
savepoint is rolled back, nothing is written and no `zone.update` row is audited. With the multi-building switch off, or the reach
setting "מיקום במפה", the guard does nothing (the routes are exactly as before).

On the four link-dropping routes the route's own permission already covers the floor / building the area leaves, so the guard
cannot refuse a caller who passed it today; what it adds there is the `mapping_changed()` re-scope of open sockets (and the D-12
installation-wide rule should a fallback ever map an unmapped area). No API shape changed, no new text, no UI change.
