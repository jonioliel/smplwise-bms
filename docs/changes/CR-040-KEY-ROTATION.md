## 1. Terms

- **Trust key**: the pairing secret (`bridge.secret` in Arx, the config entry's pairing code in the bridge) - the HMAC key of every
  signed message between Arx and the bridge (`execute`, schedules, automations, cast, media, stream source, the directory push, the
  CR-033 door messages). One key per side at every instant.
- **Trust epoch**: a positive integer, the non-secret id of the key generation. A pairing made before bridge 0.8.1 is epoch 1. A
  rotation moves `e` to `e + 1`; a re-pair starts again at 1. The bridge's value is authoritative; Arx mirrors it.
- **Rotation request**: `request_id` (lower-case UUID4 generated by Arx, never reused), the logical initiator (Arx user id and display
  name), `epoch_from`, `epoch_to = epoch_from + 1`, a 32-byte random salt (wire only, never stored or logged by Arx).

## 2. Protocol `smplwise-bridge-trust-v1` (Arx <-> bridge only; WisKey is not involved)

Transport, as the CR-033 door services: `POST /api/services/smplwise_bridge/trust_rotate?return_response` (and `trust_status`),
`service_data = {"signed_message_json": "<the wire message as ONE string>"}`.

Wire message (closed schema at every level; unknown fields refused):

| Field | Constraint |
|---|---|
| `protocol` | exactly `smplwise-bridge-trust-v1` |
| `action` | `trust_rotate` or `trust_status`, equal to the service called |
| `actor` | exactly `{id, display_name}`, each 1-128 code points without control or format characters (the door DTO rule) |
| `params` | rotate: exactly `{epoch_from: int >= 1, salt: 64 lower-case hex}`; status: exactly `{target_request_id: UUID}` (not the message's own id) |
| `request_id` | lower-case UUID4 |
| `issued_at`, `expires_at` | `YYYY-MM-DDTHH:MM:SSZ`; `0 < expires_at - issued_at <= 30` s |
| `ts`, `nonce`, `sig` | `ts == epoch(issued_at)`; 32 lower-case hex; 64 lower-case hex |

Signing is the existing recipe (DTO v3 section 3): HMAC-SHA256 over `ts.nonce.sha256(canonical body)`. The signed text is at most
4096 UTF-8 bytes.

Validation order (each stage only after the earlier ones pass; a refusal names the stage and code, never input):
`transport` -> `encoding` -> `parse` (strict JSON: duplicates, NaN, floats, unsafe integers refused) -> `schema` -> `binding`
(`ts_mismatch`, `action_service_mismatch`, `target_is_self`) -> `signature` (one key, constant time) -> `time` (`clock_invalid` below
2026-01-01, `lifetime_invalid`, `not_yet_valid`, `expired`) -> `state` (`replay` through the bridge's ONE nonce cache shared with
every signed service, `request_seen`, `epoch_mismatch`, `storage_unavailable`).

Key derivation (both sides, byte-identical code, pinned by shared vectors):
`K_next = base64url(HKDF-SHA256(ikm = UTF-8(K_cur), salt = salt, info = "smplwise-bridge-trust-v1|epoch|<epoch_to>|<request_id>", 32 bytes))`.

Answers (closed shapes; `proof = HMAC-SHA256(key, "smplwise-bridge-trust-v1|<kind>|<fields...>")`, a domain-separated MAC that never
leaves the response):

| Situation | Answer |
|---|---|
| refused before the schema passed | `{"result": "rejected", "stage", "code"}` |
| refused after it | `{"result": "rejected", "stage", "code", "request_id"}` - nothing changed on the bridge |
| rotation applied | `{"result": "rotated", "request_id", "epoch": epoch_to, "proof"}` with `proof` under `K_next` |
| status | `{"result": "status", "request_id", "target_request_id", "target": "applied" or "not_applied", "epoch", "proof"}` with `proof` under the key that verified the query |

A status query for a target the bridge has never seen **fences** it: the id is written to the ledger as `fenced` before the answer, so
the original rotation message can never be applied later (it is refused `state/request_seen`). The key under which the bridge
accepted a status query is, by construction, the bridge's current key: that is what Arx resolves on.

## 3. State machines

### 3.1 Arx (one row per request in `bridge_trust_rotations`)

```
            (preconditions fail: no row, 4xx/5xx with a clear message, audited "refused")
request ──► dispatching ──answer "rotated" + valid proof──────────────► rotated      (terminal; K_next in force)
               │      ──definite refusal / never sent─────────────────► not_rotated  (terminal; K_cur in force)
               │      ──no or unreadable answer / crash──► unknown ──status check──► rotated | not_rotated
               │                                              │
               └──────────────── re-pair (regenerate) ────────┴──────────────────────► superseded (terminal)
```

- At most one row is open (`dispatching` or `unknown`): a unique index on `open_slot` enforces it in the database.
- Terminal rows never change state again (a trigger refuses it): "never re-opened". Rows are never deleted (a trigger refuses it).
- `dispatching` is written and committed before the call leaves (two-phase): after a crash it reads as "may have been dispatched" and
  becomes `unknown` (`interrupted`) at the next start.
- Status-check resolution, in order: (1) query signed with the pending `K_next` accepted with `target: applied` -> `rotated`;
  (2) else, refused at stage `signature`: query signed with `K_cur` accepted -> `not_rotated` (`fenced`; or `reverted_on_bridge` when the
  ledger says applied but the bridge holds `K_cur` again, e.g. after a Home Assistant restore); (3) both refused at `signature` ->
  stays `unknown` (`neither_key`: re-pairing is needed); transport failure -> stays `unknown`. A status check never re-sends the
  rotation.

### 3.2 Bridge 0.8.1 (`trust.py`, pure; `trust_service.py`, the Home Assistant glue)

Held in memory: the one `Verifier` every signed service shares (its key and its nonce cache). Persisted in a private, atomically
written store `smplwise_bridge.trust`: `{entry_id, pairing_id, key, epoch, rotated_at, ledger}`. All trust operations run under one
`asyncio.Lock`, verification included. A rotation: validate -> derive `K_next` -> **persist** (the new key, `epoch + 1`, the ledger
entry `applied`) -> **swap** `verifier.secret` (one assignment on the event loop: the atomic switch) -> mirror key and epoch into the
config entry (best effort) -> answer. A persistence failure answers `state/storage_unavailable` and switches nothing; nothing can fail
after the swap. The nonce cache is never cleared by a rotation; the ledger is never pruned.

Start-up reconcile: the store wins when it belongs to the same config entry and the same `pairing_id`; otherwise (a new entry, or a
re-pair through the config flow, which writes a new random `pairing_id`) the config entry's code is the key at epoch 1 and the
ledger is kept. A store that cannot be read leaves the rest of the bridge running on the config entry's (mirrored) key and refuses
every trust operation with `state/storage_unavailable` - the ledger is never overwritten.

## 5. Permission and API

`access.trust.rotate` ("בקרת כניסה: החלפת מפתח האמון של הגשר"): sensitive (in `sensitive_permissions_not_implied`: a custom role must
name it explicitly), not a system permission (any role may carry it), never delegable through the T082 allow-list (a role with a
sensitive grant never is), installation scope only, default holder `system_admin`. Every route also requires an interactive session
(Ingress, an Arx browser session or the developer identity; never a bearer-token client) and is local-only (`BLOCKED_ON_REMOTE`).

| Route | Does |
|---|---|
| `GET /api/v1/ha/bridge/trust` | the view: epoch, bridge version / support / last confirmed epoch, the open request, the last 20 results, whether a rotation can start and why not |
| `POST /api/v1/ha/bridge/trust/rotations` `{confirmed: true}` | one rotation, synchronously (sections 3, 6); returns the outcome and the refreshed view |
| `POST /api/v1/ha/bridge/trust/rotations/{request_id}/check` | the status check of an open request (6 per minute per person); returns the outcome and the view |

## 6. Requests in the middle, failures and restarts

The gate: while a row is open, `ha_bridge.signing_key()` - the one place every outbound signed call and every inbound verification
takes the key from - refuses with `409 bridge_rotation_in_progress` ("הפעולה לא נשלחה: מפתח האבטחה של החיבור לתשתית המערכת מוחלף
כרגע. נסו שוב בעוד רגע.", `details.outcome = "not_sent"`). Nothing is queued or retried. The discovery announcement (which carries
the pairing code to Home Assistant) is skipped while a row is open. A call signed before the gate closed that reaches the bridge after
the switch is refused at stage `signature` (nothing executed); a door command whose answer is lost stays UNKNOWN and is resolved by its
own `door_open_status`, signed under whichever key is then current - its record lives outside the trust state and is untouched.

| Event | Result |
|---|---|
| precondition fails (no permission, not interactive, not confirmed, bridge older than 0.8.1 or without the capability, not paired, Home Assistant not configured, a rotation already open) | refused before anything is written; no row; audited |
| connection to Home Assistant never made (`ConnectError` / `ConnectTimeout`) | `not_rotated` `not_sent` |
| service missing (older bridge), Home Assistant refused the token | `not_rotated` `bridge_outdated` / `ha_forbidden` |
| bridge refusal (any stage, incl. `storage_unavailable`) | `not_rotated` `refused:<stage>/<code>` |
| timeout, dropped connection, HTTP 5xx, malformed answer or a proof that does not verify | `unknown` (`transport`, `bridge_error`, `invalid_response`) |
| Arx crashes after committing `dispatching` | next start: `unknown` `interrupted`; gate stays closed |
| bridge crashes before persisting | status check: `not_rotated` (`fenced`) |
| bridge crashes after persisting, before answering | status check: `rotated` |
| Home Assistant restored from an older backup after a rotation | the bridge holds the old key: Arx's calls fail at `signature`; re-pair (no automatic fix) |
| an `unknown` row | resolved by a status check: manual (button) or the 30 s janitor (first check 35 s after the request, then at most once a minute) |
| re-pair while a row is open | the row becomes `superseded` (`repaired`), the pending key is deleted, the epoch restarts at 1 |

## 7. Bridge 0.8.1 and how Arx detects it

The contract changes, so the bridge goes to **0.8.1** (manifest, `const.py`, the card's version, both copies): two new services,
`trust_epoch` and `trust_rotation: 1` in the signed directory push, `pairing_id` / `trust_epoch` in the config entry (written by the
config flow; a discovery whose code equals the current key no longer reloads the entry). Older add-ons ignore the new push fields.
Arx follows the `MIN_BRIDGE_FOR_TRUSTED_PATH` precedent: `MIN_BRIDGE_FOR_ROTATION = "0.8.1"`, compared with the version of the last
verified push, AND the capability flag of that push. Either missing: the screen shows "נדרש עדכון של רכיב החיבור לגרסה 0.8.1" and the
route refuses `rotation_unsupported`. Collision note: CR-033 planned 0.8.1 for the `execute` block (D5a, not built); whichever
lands second takes 0.8.2.

## 10. Threat table

| # | Threat | Control | Residual |
|---|---|---|---|
| T1 | Two keys valid at once (a leaked old key keeps working) | the bridge holds one key; persist-then-swap is one assignment; Arx signs nothing while a row is open | none by design; proven on the real bridge core in tests (not on a live bridge) |
| T2 | Replay of a rotation message | `request_id` ledger (never pruned) + `epoch_from` check + the key changes with the rotation + nonce cache | none |
| T3 | Replay of an old door / execute message after rotation | signature under the new key fails; anti-replay records are never deleted, so a message within its window stays a replay | none |
| T4 | Late delivery of a rotation message after Arx decided "not rotated" | the status query fences the id before answering; the message's lifetime is 30 s | none |
| T5 | Request in the middle executed twice or silently retried | gate refuses before signing; UNKNOWN resolved by status only; terminal rows cannot reopen (trigger) | an operator may start a NEW rotation after `not_rotated` (a new id) |
| T6 | Key material leaks through audit, logs, screens, backups, fixtures | section 9; `bridge.trust.` settings never exported or restored; tests scan everything | the bridge's config entry and store (Home Assistant `.storage`, private) hold the current key, as before |
| T7 | Unauthorised rotation (lock-out of the bridge as a denial of service) | `access.trust.rotate` (sensitive, installation scope, not delegable), interactive session, local only, explicit confirmation, audited | a holder can rotate repeatedly (each is audited; nothing breaks) |
| T8 | Attacker who already holds `K_cur` AND observes the rotation call (salt) derives `K_next` | out of scope of rotation: in this deployment such access also exposes the config entry; for a suspected leak, re-pair with a fresh random key | stated limitation; no forward secrecy against a passive holder of the old key |
| T9 | Discovery announcement reverts a switched bridge to the old code | announcement skipped while a row is open; the config flow does not reload on an unchanged key | none |
| T10 | Desync after crash on either side | two-phase marker, persist-before-answer, status check with fence, start-up recovery | `neither_key` needs a re-pair (fail closed) |
| T11 | Clock manipulation to replay or pre-date | 30 s lifetime, no forward skew, 2026 floor | the bridge trusts the host clock (as every signed path does) |
| T12 | Capability or WisKey state silently relied on across a rotation | no capability or mapping depends on key bytes; nothing is claimed about capability survival (NOT_PROVEN) | WisKey-side behaviour unverified |
| T13 | The existing pairing route shows the current key to `system.configure` holders (also remotely) | unchanged by this CR (manual pairing needs it) | follow-up: local-only and an audited reveal (recorded, not built here) |
