# TPLV2-295 - WhatsApp template send v2, Arx side (board item "WisKey A08", version 2.21.0)

**Status:** built on `pilot/TPLV2-295` (base `origin/release/2210` 3dd7b8c46). **OFF by default, fake station only.**
Nothing here has run against a real WisKey, Mac station, queue, Home Assistant or phone.

Owner decision 25.10: no consent flag - an open conversation window is enough; the version is not held if WisKey has not answered.
Consequently no consent value is read or sent by this flow (the former TP-02 rule, unchanged). Arx's own opt-out list (a person who
asked not to be messaged) is a different rule and still refuses (see Q4).

## 1. What is built

| Piece | File |
|---|---|
| ONE contract/constants module: every WisKey-defined name (command, schema versions, closed keys/results, pacing schema version) re-exported in one place with a status per item (`ADOPTED_W013` or `UNCONFIRMED`); `DIRECT_STATION_VERIFIED = False` | `smplwise/services/wa_template_v2_contract.py` |
| Flow: binding token, preview blockers, short-transaction pacer (the write gate is not held while waiting for WisKey), sender builder, honest verdict mapping | `smplwise/services/wa_template_v2_flow.py` |
| Routes (below) | `smplwise/routers/access_control_template_v2.py`, registered in `main.py` |
| Tests (38, fake only) | `tests/test_tplv2_295.py` |
| The send itself (existing, unchanged): `TemplateSender.send_v2`, `TemplateRequestV2`, `read_v2`, `DirectTemplateTransport.send_v2` | `wa_template_send.py`, `wiskey_template_direct.py` (WK4ADOPT-295 / WKR5-295) |

Routes (all under `/api/v1`):

| Route | Gate | What |
|---|---|---|
| `GET/PUT /access-control/messaging/template-send` | `system.configure` (per-role through the normal role assignment) | the switch `messaging.template_send` (default OFF), the template references (name, language, slots, purpose, WisKey's private `template_ref` + `template_revision`), the code permit, the contract status. PUT is validated (422 `template_send_invalid`, every problem as `{path, code}`), audited with names and counts only |
| `POST /access-control/people/{id}/messages/template-v2/preview` | `access.people.message` on the person's stations | what Arx would hand over; `content_shown: false` (WisKey fills the values, Arx cannot show the text); `window: "unknown"`; `blockers`; `can_send`; a binding `token`. Sends and records nothing |
| `POST /access-control/people/{id}/messages/template-v2` | same | explicit `confirmed: true` + the preview `token` + `client_request_id`. Attempt record + audit row BEFORE the hand-over (the existing `intercom_messages` record and `begin_attempt`/`finish_attempt`), then the outcome row |

Gates in order: confirmation, messaging enabled, send hours, template reference exists, switch ON, permit open, WisKey pair bound,
person revision known, messaging account connected, opt-out list, token still matches (409 `template_v2_preview_stale` when the template
or the person changed after the preview), attempt caps (`begin_attempt`), the shared send budget (`wa_pacing`, class `ticket`, counted
once), the window rule (`unknown` is treated as closed), then one `send_v2` hand-over on the wiskey-bridge-command path.

Honest outcomes (`intercom_messages.outcome`, HTTP): `sent` = the provider accepted it, delivery stays unknown (200); `not_sent` =
decided locally, nothing left Arx, the attempt row is removed (409/422/429/410/503); `refused` = a closed WisKey `not_sent` result
(502 `template_v2_refused`); `unknown` = anything else - no answer, exception after the hand-over, a v1 result, a malformed result, a
result claiming delivery, WisKey's own unknown (504 `message_uncertain`, never retried, never shown as sent or as failed). An unknown
person revision is `person_revision_unknown` (blocker), never replaced by a made-up number.

The send is wired to the fake only through `wiskey_template_direct`/`TRANSPORT_V2_PROVIDER`, which the direct join sets while
`whatsapp/template_send_v2` is selected on the live connection; with no provider the flow refuses `template_v2_unavailable` before any
hand-over (test).

## 4. Open questions for WisKey (UNCONFIRMED in `wa_template_v2_contract.ITEMS`)

1. **Numbered contract:** is `W013_TEMPLATE_SEND_V2.json` revision 2 (CODE 924df3e9, items 1-9) final, and what is the final contract
   number/name? Arx adopted it as `ADOPTED_W013` but only against its own fake.
2. **`expected_person_revision`:** is it the `revision` of the `users/get` record (what Arx reads), or a different counter?
3. **`pacing_schema_version`:** is a v2 template send charged to the counters of `pacing_status_v1` (version exactly 1)? Is a template a
   different cost class than a free-text message?
4. **Throttling on v2:** no closed `not_sent` code exists for a rate/pair throttle (so `retry_after_s` stays empty). Will there be one?
5. **Conversation window:** WisKey exposes no window state. Confirm that the station itself picks template vs free text, or that a
   template inside an open window is accepted (Arx treats `unknown` as closed and sends the template).
6. **Execution source and production queue** on the Mac: installed? (Last answer 23.10: not installed.) Which installer read point
   (`native_whatsapp_templates_v1`) does the owner use to register `template_ref`s, and how does an administrator learn each
   `template_ref` / `template_revision`?
7. **Idempotency:** Arx sends `request_id = client_request_id` and `operation_id = "tplv2-" + client_request_id`. Is a repeat of the same
   `operation_id` guaranteed to be answered `operation_pending_or_unknown` (or the original result) and never sent twice?

Question for the owner (not WisKey): Q4 - should a person on Arx's own opt-out list still be refused for a template (current behaviour,
`message_no_consent`), given the decision "no consent flag"? The opt-out is an explicit "do not message me", not a missing consent.
