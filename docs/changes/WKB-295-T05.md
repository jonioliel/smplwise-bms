# WKB-295 T05: the durable full original of a WisKey people write

Status: built and tested with fakes only. Branch `pilot/WKB-295` (from `origin/main` 90cd7d9ae, release 2.12.1), then
`pilot/WKB2-295` (from `pilot/WKB-295` 812b49a1d) for the owner decision of 2026-10-23 (section 7).
Nothing is wired. No route or sync path calls the new functions. The only new runtime hook is the retention purge in the janitor
(section 7.3); it touches nothing until an intent admitted through `admit_with_original` exists. No switch or `GO_LIVE_PERMITTED`
constant changed. Nothing was run against WisKey, Home Assistant or a station.

## 1. What WisKey asked (T05, their answer of 2026-10-22)

1. The intents table (migration 0145, `services/wiskey_intents.py`) does not close a durable FULL original:
   `ExactOriginal.as_request` is refs-only, unfit for `peer_receipts` / `resolve`.
2. The full original, its hash and the verified context must be recorded in a COMMIT completed BEFORE any I/O. Crash and restart
   must be tested.
3. pin / epoch / exclusive-writer must come from an agreed source, never assumed.
4. An old intent without an original stays UNKNOWN: no reconstruction, no replay, no extra create.
5. The proposal `person_writes/resolve_create` is not an alias of the existing path.

this path, and `LiveResolveTransport` still refuses `not_built`.

## 3. Tests (`smplwise_vms/backend/tests/test_wkb_295.py`, A05 part)

The tests use a file database opened by separate connections to simulate another process or a restart:

- After `admit_with_original` returns, a second connection sees the intent, the full original, its hash and the context. The
  connection is not inside a transaction.
- A failing original insert (a test trigger) leaves no intent row: the admission is atomic.
- Crash after `sent` was committed: the transport is entered, then the process dies with a `BaseException`. After restart the state
  is `sent` and the plan says `resolve_with_original`. The resolve body carries the full original and the hashes. A new send is
  `not_sendable` and the transport is not called.
- Crash between the admission and the send: after restart the plan says `held_not_sent`. A send under a new epoch is refused
  (`epoch_changed`), nothing is sent and the state stays `intent`.
- A transport error commits `unknown` and is never retried.
- An old intent admitted through `admit`, with no original, stays `unknown_no_original`. Both `resolve_request` and `send_once`
  raise `no_original`, and the state is not moved.
- These contexts are refused: a dict, a `FenceContext`, one without the exclusive writer, another repository, another owner. The
  sealed context cannot be forged.
- These originals are refused before anything is written: PIN, nested card number, cards list, float, unsafe int, message id,
  empty, too large.
- Immutability triggers on the original and on the intent selectors; the state still moves. A tampered original is
  `original_corrupt`, and recovery classifies it `unknown_no_original`.
- A duplicate keeps the first original.

## 4. What must come from WisKey (definition needed; Arx stops at the interface)

1. **The agreed source of pin / epoch / exclusive writer.** Arx has the owner pin (`wiskey.peer_pin`, `wiskey_peer_registry.OwnerPin`)
   and the sealed `VerifiedPeerRef` minted only by the registry client. Neither the registry read (`peer_bindings/get`) nor the
   transport is delivered. For the writer epoch and the exclusive-writer fact there is NO source in Arx's code. The r9 draft named
   `person_writes/context`; it is not delivered. WisKey must name the command, its result fields, how fresh it must be, and whether
   `exclusive_writer_established` is per connection, per owner or per repository. Until then `_mint_write_context` has no caller and
   `admit_with_original` cannot run in the product.
2. **The exact bytes of "the full original".** Arx records the request object it would send, without the per-connection message
   `id`. WisKey must say whether the hash is over this canonical JSON (`arx-json-c14n-v1`), over the exact wire bytes, or over its
   own canonical form. It must also say whether `operation_id` / `request_id` must appear inside the original, and which hash
   algorithm and encoding it expects.
3. **The wire shape of the resolve** (`peer_receipts` / `resolve`). `resolve_request` is Arx's proposal only.
4. **PIN- and card-bearing originals.** Arx refuses to store a secret or a hash over it. WisKey must say how such a write is
   identified: for example a WisKey-side commitment Arx never sees, or a salted keyed hash held by WisKey.
5. **What "verified context" means to WisKey**: which fields it compares at resolve time. Arx records repository, owner, epoch,
   exclusive writer, source, verified peer ref and peer binding ref + revision.

## 7. Owner decision 2026-10-23 (WKB2-295): keep the table, protected

The owner decided to keep `wiskey_intent_originals` with five protections. Branch `pilot/WKB2-295`. The migration number 0146 stays
provisional; the table and its triggers were changed in place (0146 is not released).

### 7.1 References, not personal details

- The original names a person by REFERENCE only: WisKey's person id, the expected revision, the door references.
- `wiskey_intents.PERSONAL_KEYS` lists display-name and contact keys, for example `name`, `display_name`, `first_name`, `last_name`,
  `email`, `phone`, `address`, `national_id`, `photo` and `face`. The match is case-insensitive and applies at any depth. An original
  carrying one is refused with `personal_in_original`, and nothing is written.
- Such keys are refused, NOT stripped. The recorded bytes are exactly the bytes `send_once` sends, so a stripped original would be a
  different write.
- Definition needed (WisKey): how a write that changes a person's name is expressed by reference. Until then, Arx cannot admit such
  a write through this path.
- PIN, card, password, token, secret and credential keys stay refused (`secret_in_original`), and the tests keep them.

### 7.2 Sealed at rest

- The canonical original and the canonical context are sealed with the same mechanism as the bridge keys, `connection_store`
  `seal_wiskey_intent` / `open_wiskey_intent`: AES-256-GCM, the per-install key file `keys/connections.key`, `v1:` blobs. There is
  no new crypto.
- The associated data is `wiskey_intent|<sha256 of [repository, query owner ref, operation id]>|original|context`. A blob copied to
  another intent, to the other field, to another store or to an NVR row does not open.
- Both SHA-256 values are computed over the canonical PLAINTEXT before sealing. They stay in clear as the proof of what was sent.
- The seal happens before the transaction (no key-file I/O under the write lock). The commit is unchanged: the intent row and the
  sealed original are committed together, before any I/O.
- Reading never creates a key. A blob that does not open is `original_unreadable`.
- Honest limit (as for every `connection_store` secret): the key lives beside the database. This protects a leaked database file or
  an Arx backup. It does not protect against a reader of the whole data folder, and a Home Assistant add-on backup contains both.

### 7.3 Retention and purge

- The setting is `wiskey.intent_original_retention_days`. The default is 30 days, clamped to 1..365. A saved 0, a negative value
  or junk never turns the purge off and never purges "now": 0 and negatives become 1, junk becomes 30, and values above 365 become
  365. There is no UI for it yet; it is a stored setting.
- The purge is `wiskey_intents.purge_originals`, run by `services/wiskey_intent_retention.janitor` from `main.janitor_tick`, at
  most once an hour per process, the same way as `pending_retention`. A failure is logged by type only.
- It nulls `original_enc` and `context_enc` and stamps `purged_at` for every intent that is TERMINAL (`committed` /
  `never_committed`) whose terminal fact (`settled_at`) is older than the window.
- The row, both hashes and the terminal state stay as proof. An open intent (`intent`, `sent`, `unknown`) is never purged,
  however old.
- It is idempotent. It writes one audit row (`wiskey.intent_original.purged`) per pass that purged something. The row holds counts
  and the window only, never an id, a hash or a value.
- After a purge, `resolve_request` and `send_once` raise `no_original`. A purged intent is terminal, so recovery never lists it.
- Trigger `wiskey_intent_originals_guarded` allows only this one UPDATE. Its conditions:
  - both sealed columns go to NULL and `purged_at` is set, once only;
  - every other column is unchanged;
  - the intent is terminal;
  - `purged_at` is at least one day after `settled_at` (0.999 d, a float tolerance).

  Any other update is refused, including one the condition cannot evaluate. DELETE stays refused. The trigger is defence in depth:
  it trusts the `purged_at` the writer supplies.

### 7.4 Backup and restore

- `wiskey_intent_originals` is in `backup.NEVER_EXPORTED_TABLES`, next to `wiskey_fence_intents`. It is never written to an Arx
  backup archive (neither the plain export nor the sensitive section), and a restore never touches it.
- After a restore onto the SAME installation, the table and its key are untouched, so recovery is unchanged.
- After a restore onto another installation, neither the intents nor their originals exist there. Nothing is reconstructed.
- After a database file comes back without its key file (an add-on restore elsewhere, a copied file), no sealed original opens.
  Every open intent is then `unknown_no_original` in `recovery_plan`. `resolve_request` raises `original_unreadable`, and
  `send_once` refuses and sends nothing.
- In every case there is no reconstruction, no replay and no extra create.

### 7.5 API change

`admit_with_original` needs `data_dir=` (the folder whose `keys/connections.key` seals the original). `stored_original`,
`send_once`, `resolve_request` and `recovery_plan` need it to open it. There is no product caller yet, so nothing else changed.

### 7.6 Tests added (`tests/test_wkb_295.py`, negative tests first)

- The database file bytes (and any journal) never contain a value of the original, a value of the context or the canonical JSON.
  The stored hash equals SHA-256 of the canonical plaintext, and there is no `original_json` column.
- Names and contact fields are refused (`personal_in_original`) at any depth. PIN, card, password and token are still refused.
- The purge runs only for terminal intents past the window. Recent terminal intents and open intents (`intent`, `sent`,
  `unknown`) are never purged, however old. The hash and the state stay, and the purge is idempotent.
- The window clamps to 1 and 365.
- `resolve_request` works from the sealed original and raises `no_original` after the purge.
- The triggers refuse:
  - the purge shape on an open intent;
  - a purge sooner than one day after the terminal fact;
  - a hash change;
  - nulling one column only;
  - a new sealed value;
  - an unparseable time;
  - any change after the purge;
  - DELETE.

  The state columns still move.
- Backup: `snapshot` and the archive carry no row and no file of either table, and a value of the original and its hash are absent
  from the archive bytes. A restore keeps the same installation's originals readable. The same database without its key gives
  `unknown_no_original` / `original_unreadable`, and nothing is sent.
- The janitor purges, audits counts only, is idempotent and never raises. `janitor_tick` calls it.
- A tampered hash is `original_corrupt`. A sealed blob moved from another intent is `original_unreadable`. Recovery lists both as
  `unknown_no_original`.
