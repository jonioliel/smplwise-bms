# I18N-ARRU-2550 - Arabic and Russian for every key of the four-language catalogues

Target 2.55. Base: `origin/release/2550-train` `5aa03829b`. Branch: `pilot/I18N-ARRU-2550`.

## Why

The interface has four languages (he / en / ar / ru) in the catalogues that offer them; Arabic / Russian are reached through
`<html lang>` (an embedding page; the product's language switch offers Hebrew and English only). Keys added later to four of those
catalogues were written in Hebrew and English only, so an Arabic or Russian page showed those words in Hebrew. The project had a
completeness ratchet for English (`unit-i18n-en-ratchet-2490.spec.ts`) but nothing for Arabic / Russian, so the gap grew unseen.

The missing ar and ru sets were identical (the same keys in both languages).

### Hebrew / English only on purpose (left as they are)

- **121 frontend catalogues have no Arabic / Russian table at all**: the main catalogue `i18n/he` (1,368 keys), 34 module catalogues
  (`access-*`, `wiskey-*`, `notices`, `maintenance`, `insights`, `home-screen`, `presence`, `scenarios`, `schedule-editor`,
  `xsection`, `transit`, ...), 26 tickets catalogues (`tickets/*`), `water/i18n`, the 30 source-text tables `msg/*` and a few small
  ones. A catalogue declares its languages (`createCatalogue(name, he, { en, ar, ru })`); these declare English only. As
  `GEN-UNITS-ARRU-2530.md` records, the main catalogue has no Arabic / Russian column anywhere in the product; the owner's standing
  rule for new texts is Hebrew + English. They are listed implicitly: `docs/i18n/ARRU_COMPLETENESS.json` names the four-language
  catalogues, every other one is Hebrew / English only.
- **Server refusal and screen texts** (`smplwise/i18n.py` `LANGS = ("he", "en")`, `error_text_en.json`, `error_text_tpl_en.json`,
  `details.message_en`): the interface language a user can store (`ui.lang`) is Hebrew or English. There is no Arabic / Russian server
  catalogue to fill.
- **Server documents** (temperature PDF / WhatsApp summary, CSV exports): the routes accept `lang: Literal["he", "en"]`.
- **Server messages to people outside the product** (technician codes, access requests, announcements and their templates, ticket
  messages and RFQ texts, WhatsApp notices) are already four-language: an AST scan of `smplwise/` found 75 he/en/ar/ru dictionaries and
  no he/en-only dictionary in those files (the only he/en dictionary there, `announcements.MESSAGES`, is the refusal text above).
- **Public pages** (`public-ticket/`): their own four languages, already guarded by `unit-public-ticket.spec.ts` ("every language has
  every key").
- Small inline tables typed `Record<'he' | 'en' | 'ar' | 'ru', ...>` (`nav-labels.ts`, `settings-nav-strings.ts`, `announce/screen-overlay.ts`,
  `tickets/naming.ts`) are complete by type; `generator/gen-text.ts` carries only the unit words in ar / ru on purpose
  (GEN-UNITS-ARRU-2530).

## What changed

- `frontend/src/i18n/lang/{ar,ru}/i18n/{temperature,elevators,generator-log,door-automation}.ts`: the 669 missing keys per language,
  appended under a marker comment (the existing entries are untouched). Initial translation, dev-marked like the rest of these tables
  (`*_DEV_MARKED = ['ar', 'ru']`); a native review is still needed. Every `{placeholder}` is kept exactly as in the Hebrew (checked by a
  script and by the new spec); no plural forms exist in these catalogues (they use `{n}` only).
- Word choices, kept consistent with the existing ar / ru words of the same modules:
  - Arabic: the singular unit after a figure (`{n} دقيقة`, `{n} ساعة`, `{n} يوم`, `{n} ثانية`), as GEN-UNITS-ARRU-2530 chose; unit =
    وحدة, sensor = حساس, alarm / warning = إنذار / تحذير, defrost = إذابة الجليد, mute = كتم; the arrows of the fuel events stay `←`
    (right-to-left, as the Hebrew). Arabic reads right-to-left by the page direction; no direction marks are needed in the texts.
  - Russian: short units that need no plural agreement (`мин`, `ч`, `с`, `дн.`), counts written as `label: {n}` (`блоков: {n}`,
    `событий: {n}`) for the same reason; unit = блок, setpoint = уставка, the fuel arrows `→`.
  - Days of the week of the temperature schedules (`dow0` = Sunday, as the Hebrew week).
- `frontend/src/i18n/generator-log.ts`: the header comment (ar / ru now cover every word).
- `scripts/i18n_missing_keys.mjs` (report only): with `--lang ar` / `--lang ru` a row also lists `scriptKeys` - a text in the other
  language's letters (Cyrillic in an Arabic text, Arabic in a Russian one); a source-text table (`msg/*`) without a table of the
  language now says `hasTable: false` (it said `true` and counted every key as missing). English output unchanged (`gap 4`,
  `placeholder 1`, as before).
- `docs/i18n/ARRU_COMPLETENESS.json` (new, hand-edited): the 37 four-language catalogues, and the 5 keys allowed to differ, each with
  its reason (the two confirmation words of `access-external` the user types in Hebrew and the language self-names of `announce`, the
  same keys `EN_RATCHET.json` allows for English).
- Tests:
  - `frontend/tests/unit-i18n-arru-completeness-2550.spec.ts` (new, Node): runs the report for ar and ru; the catalogues with ar / ru
    tables must be exactly the listed ones; in them every key has its ar and ru text, with the Hebrew's placeholders and no other
    language's letters, except the listed keys; a listed key that is fixed fails too (the lists only shrink). **It fails** on a new key
    without ar / ru - see question 1.
  - `frontend/tests/evidence-i18n-arru-2550.spec.ts` (new, browser): the temperatures screen, the elevators screen and the generator
    run log on an Arabic and a Russian page, light and dark: no Hebrew text node is left inside the module (the fake data names of the
    mocks excepted); the page direction is right-to-left for Arabic, left-to-right for Russian. Pictures with `SW_ARRU_SHOTS`.
  - `unit-elevators.spec.ts`, `unit-temperature.spec.ts`, `unit-genlog-tempexplain.spec.ts`: each used an untranslated key as its
    "falls back to Hebrew" sample; those keys are translated now, so they assert the new word and that the module has no ar / ru gap
    (the fallback itself is covered by `unit-i18n-core.spec.ts`).
- Unchanged: Hebrew and English texts, `he.ts` / `en.ts`, element ids, `data-*` hooks, request bodies, saved data, server code, design
  tokens. No screen changes in Hebrew or English, so no pixel baseline changes (the pixel suites have no Arabic / Russian cases).

## Open questions (recommendation first)

1. A new key in a four-language catalogue without Arabic / Russian: (a) the new spec FAILS (as implemented; same strictness as the
   English ratchet; a row that cannot translate lists the key in `ARRU_COMPLETENESS.json` with a reason); (b) report only (a warning
   line, never fails).
2. Native review of the Arabic and Russian (all dev-marked): (a) before Arabic / Russian are offered in the language switch;
   (b) now, for the four catalogues of this row only.
3. The 121 Hebrew / English-only catalogues (about 29,000 keys, including the main catalogue): (a) stay Hebrew / English until the
   owner decides to offer Arabic / Russian in the switch; (b) translate the resident-facing screens first (notices, home screen).
