# T068-EDGE-2450 - soak edge cases: disconnects and a full disk

Branch `pilot/T068-EDGE-2450` from `origin/release/2440-train` @ `e9d17b5ab`. Card T068 (AT135 / AT136; the card stays PARTIAL
until the long soak is re-run with these fixes). Targets 2.45.0.

The soak harness (`T068-SOAK-2406`) and its fixes already cover scale and scheduled device restarts. What was missing were the edge
cases: disconnects walked through a whole cycle with assertions, and a full disk. They are automated tests on fakes and temporary
folders only - no lab, no device, no Home Assistant.

## What every edge test checks

1. nothing crashes (the worker / listener / sync thread is still alive, the API still answers);
2. a health or diagnostic signal says what is wrong while it is wrong (top-bar summary, administrator's report, a counter or a state
   field) and stops once it is over;
3. recovery happens on its own when the condition clears (no restart, no manual step);
4. data committed before the fault is still there afterwards, and `PRAGMA integrity_check` is `ok`.

## Product fixes (separate commit)

1. **Export cut off by a full disk while it is being finished** (`services/exports.py`). The download loop paused a job on a full
   disk, but a full disk during the finish (remux, zip, the manifest) fell into the generic "post-processing failed" path: the raw
   fallback ran again and the job ended **`done` without `manifest.json`** (the integrity record of an evidence export), with an
   English note. Now an `ENOSPC` there - or any finish failure while free space is under `storage.min_free_mb` - removes what the
   finish wrote (`_unfinish`: downloaded files still on disk are kept, a file the finish had consumed is downloaded again) and
   pauses the job exactly like a download pause (`_pause`, the former inline block, unchanged in behaviour); the worker resumes it
   when there is room and it completes with its manifest.
2. **A full disk flooded the log** (`db.log_storage_full`, used by `events_ingest` and `ha_sync`). Every refused alert and every
   refused HA state change logged a full traceback - at the soak's rates ~26 tracebacks a second, onto the disk that is already
   full. Now a storage-full refusal from these two always-on writers logs one plain line per writer per minute with the number
   refused since the last line; every other error keeps its traceback. The counts stay exact (`IngestQueue.failed`); the health
   summary's "storage" item is the operator's signal (unchanged). The limiter's state is registered for the per-test reset.

## Soak harness (`tests/soak/soak_long.py`)

- `LogPump`: the backend's stdout / stderr go through a pipe to a rotating writer (`--log-max-mb`, default 64; `--log-keep`,
  default 3). Rename rotation by the only writer (copy-truncate loses what is written between the copy and the truncate, and
  depends on the backend's handle staying in append mode). A failing write drops the chunk and counts it; the backend never
  blocks on its log.
  `summary.json` carries `backend_log` (rotations, dropped bytes, write errors).
- Disk guard: the run ends with reason `disk_low` when the run folder's disk has less than `--min-free-mb` (default 2048) free -
  the runner reached 100 % on 2026-11-18.
- Not added to the long run on purpose: filling a real disk. The runner is shared with the release gates; the full-disk edges are
  the tests above.

## Observations (no change)

- The first request of a brand-new installation writes the bootstrap administrator's grant; on a full disk that request answers
  507. Only a fresh installation is affected (the grant exists afterwards); refusing is correct - the grant cannot be recorded.
- A coverage gap is keyed by the second its outage began; two outages starting in the same second would share one row. A real
  reconnect takes at least 5 s (the listener's back-off), so this cannot happen outside a test that removes the back-off.
- HA states that changed while the socket was down reach the mirror through the snapshot on reconnect, but a tracked transition
  (a door) that happened entirely inside the outage is not recorded as an event - the existing connect-gap row marks the gap.
- Thumbnails: a failure marker that was written on a full disk blocks a retry for its hour (`NEG_TTL_S`); when the marker itself
  cannot be written (F4) the picture is asked again at once.

Why a size cap and not a mount: the server has no root and no unprivileged user namespaces (`unshare -rm` is refused), so a tmpfs or loop
device inside the folder is not possible. `max_page_count` is SQLite's own limit and produces the real `SQLITE_FULL`; it exercises the
same code (`db.is_storage_full`, the 507 handler, the writers' counters) as a full volume, but not the operating system's ENOSPC path
(that stays covered by the first pass's `OSError(ENOSPC)` fakes for files).

### Product fix

**A refused write was invisible to health when the volume still reported free space** (`db.is_storage_full`, `health_report`). The top-bar
summary and the report's storage check looked only at `shutil.disk_usage(/data)`. A quota-limited or size-limited volume (or reserved blocks)
refuses writes while `free` looks fine: the operator got 507 answers and the alert writer lost alerts with no signal. Now every handler that
recognises a storage-full error records the time (`db.recent_storage_refusal_age`, kept in the existing per-test-reset table), and for
`STORAGE_REFUSAL_WINDOW_S` (120 s) after the latest refusal the summary item `storage` and the report check are `error` with the reason
("writes are being refused: no room"). The always-on writers refuse every second while it lasts, so it stays; once space is back it ends
by itself. A system that is idle while still full falls back to the old free-space check after the window. The first-pass test F1 now waits
for the warning to clear (window set to 1 s there).

### Observations (no change; bigger or by design)

1. **A re-delivered alert increments the burst count.** The same alert (same channel, kind and device time) delivered twice produces one row
   but `count` 2: the merge cannot tell a repeat from a second genuine alert in the same second. Hikvision does not resend on reconnect in the
   lab history, so no change; a fix would need the device's own sequence number (not in the alert stream).
2. Frames for HA states that changed during an outage are not pushed one by one to `/ha/ws` subscribers; they get `ha_sync_state connected` and
   the mirror is replaced by the snapshot (the screens refetch). By design, now pinned by G2.
3. The real-OS ENOSPC path of SQLite's WAL/fsync (`SQLITE_IOERR_*` rather than `SQLITE_FULL`) cannot be produced without a small mounted volume.
   If a runner with root is available, a 4 MB tmpfs run of G1 is the next step.
4. go2rtc / NVR fakes disconnecting while a live viewer is open is covered at the relay level by the long soak (15 go2rtc restarts, 2.5 % failed
   opens); no new test here.
