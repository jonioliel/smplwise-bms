# DOOR-BLOCKS-I18N-2510 - the door blocks screen and the run guard in the reader's language

Branch `pilot/DOOR-BLOCKS-I18N-2510`, cut from `origin/release/2500-train` at `60fc78e3d` (it contains DOOR-PREVIEW-I18N-2500). Target
2.51. Follow-up of DOOR-PREVIEW-I18N-2500, open questions 1 and 2. No setting, migration, wire model or API shape change; no look change
(only the language of texts the screens already show verbatim, and three English sentences of the frontend catalogue).

## What changed

Mechanism: I18N-BACKEND-2490 (`smplwise/i18n.py`) as in DOOR-PREVIEW-I18N-2500. A text is a `Msg` whose string value IS the Hebrew the
code wrote before; the edge that answers one request renders it in the requester's `ui.lang` (no user / no stored value = Hebrew).

### Open question 2: `GET /doors/blocks` and `door_run_guard.NOT_YET`

* `services/door_conversion_text.py` (the door catalogue) gains two namespaces, 16 keys:
  * `doorguard.*` (8): `not_yet`, the four refusals built around it (`not_converted`, `unresolvable`, `enable_not_converted`,
    `enable_unresolvable`, each with a `{not_yet}` slot filled by the `not_yet` `Msg`, so the Hebrew is exactly the old f-string and
    the English follows the sentence), `no_permission`, `use_automations`, `station_unavailable`.
  * `doorblocks.*` (8): `refuse.*` (why an entity cannot be released: `unknown_entity`, `wiskey_door`, `door_mapped`, `not_blocked`)
    and `note.*` (`note_required`, `note_too_long {n}`, `bad_entity`, `too_many {n}`).
  * `as_msg(key, he, **params)`: the single-text form of `as_msgs`; it refuses at import when the module's Hebrew template differs
    from the catalogue's, so a Hebrew reader's bytes cannot drift.
  * English handwritten with the frontend catalogue's words ("The station is unavailable", "access-control", the blocks screen's
    "Release" / "intercom door" / "The reason is too long (up to {max} characters)").
* `services/door_run_guard.py`: `NOT_YET`, `NOT_CONVERTED`, `UNRESOLVABLE`, `NO_PERMISSION`, `USE_AUTOMATIONS`, `ENABLE_NOT_CONVERTED`,
  `ENABLE_UNRESOLVABLE` and the new `STATION_UNAVAILABLE` (was an inline "התחנה לא זמינה" in `open_plan_doors`) are `Msg`s. Every
  run / enable refusal of an item that opens a door therefore reaches an English user in English through the error envelope
  (`ApiError.payload(cid, lang)`), with no change at any router (automations, schedules, device tiles, the door path conversion).
* `services/door_blocks.py`: `REFUSALS` texts and `NOTE_ERRORS` are `Msg`s (the release refusals of `PUT /doors/blocks/entities/{id}`
  answer in the user's language through the envelope); an item's `why` is `door_run_guard.NOT_YET` (now a `Msg`); `kind_text`,
  `guard` and `reasons` already were `Msg`s from the inventory (DOOR-PREVIEW-I18N-2500).
* `routers/doors.py`: `GET /doors/blocks` answers through `localize_for` (Hebrew reader: the value as it is, no copy).
* Not translated on purpose (data): entity / item / device names, areas, release notes and who released.

### Open question 1: one English word for "חלון פתיחה"

"door window" everywhere. It is the frontend's own word for the feature (`i18n/lang/en/i18n/door-windows.ts`: "Door windows",
"New door window", "Edit door window"; `nav-labels.ts` tab "Door windows"; `insights.ts` "Door window") and the default name of a
handed-over window (`default_names.door_window` = "Door window", unchanged). Changed from "opening window":
* backend `doorconv.*` English (6 texts): `action.hand_over_program` "Move to a fixed door window", `why.no_end_time`,
  `why.window_too_long`, `why.invalid_time`, `why.exterior_not_allowed`, `err.program_in_use`;
* frontend `i18n/lang/en/i18n/msg/system-a.ts` (the same preview screen's own sentences, 3 values): "Move to a fixed door window",
  "Moved to a door window", "Disable the schedule "{name}" and create a fixed door window{when}? ...".
Hebrew unchanged everywhere; stored names stay as stored.

Not changed (outside this task's screens; recorded as a follow-up): "opening window" is still the English of `rbac_text.py`
(`door_windows_manager` "Manage opening windows", `door_windows_guard` "Stop an opening window"), `rbac_admin_text.py`
(`access.windows.manage` / `access.windows.guard` descriptions) and four `notify_policy_text.py` event names ("Opening window did not
start", ...). The built bundle under `smplwise_vms/www/` is regenerated by the release build, not by hand.

* `test_door_blocks_i18n_2510_hebrew_unchanged_english_for_an_english_reader` - a reader with no stored language gets the old Hebrew
  (`why` = the old `NOT_YET` literal, run guard, kind), the route's Hebrew equals the service's, and the release refusals are the old
  literals; after `ui.lang = en`: the same machine fields (keys, states, counts, entity rows, devices, releases), English kind / guard

  `too_many` rendered); the run guard's refusals through `ApiError.payload` in both languages; back to Hebrew: the same answer.
* `test_door_blocks_i18n_2510_the_enable_refusal_reaches_an_english_reader_in_english` - through the real automations route (CR-017
  world): `enable` of a door automation answers the old Hebrew `ENABLE_*` sentences, and the English ones for an English reader; the
  blocks screen's `why` / `kind_text` in English.
* `test_door_blocks_i18n_2510_every_text_has_a_key_and_no_hebrew_literal_is_left` - the key scan: 16 `doorguard` / `doorblocks` keys,
  Hebrew + English, no Hebrew letter in the English, the same slots; every run-guard / blocks text is a `Msg` of its key whose string is
  the old Hebrew (spelled out in the test); a drifted Hebrew is refused by `as_msg`; no Hebrew literal left in `door_run_guard.py` /
  `door_blocks.py` outside the catalogue (docstrings aside); "opening window" absent from every door catalogue English and from
  `msg/system-a.ts`, the default name "Door window", the frontend feature catalogue "Door windows".

`tests/test_i18n_backend_2490.py` scans the whole catalogue (Hebrew + English, English without Hebrew, same slots) and now covers the
