# 2.5.6 integration notes (integ/256)

Base `origin/main` @ `cbe5e1c4` (2.5.5). `integ/256` = main + `pilot/FIX-status-substate-256`. Nothing contacted a real device, NVR, WhatsApp account, tunnel, Cloudflare or Home Assistant: fakes and fixtures only.

## Content
- Owner request: 'waiting for a part' must not look like a mandatory step of the flow. It is a presentation change only: the API, the stored status value (`waiting_part`), the transitions, the
  SLA / stuck dues, the facets and the board sections are untouched. No backend code changed (only tests were added), no migration (last 0084), no new add-on option.
- `frontend/src/tickets/model.ts`: `STATUS_LINE` has six steps; new pure helpers `isWaitingPart`, `lineStatus` (waiting_part reads as in_progress), `chipLabel` ("בטיפול · ממתין לחלק"),
  `waitingToggle` (mark from in_progress / acknowledged when the server's transitions allow it, "back" from the sub-state) and `menuMoves` (the status menu never lists the sub-state; leaving it reads "חזרה לטיפול").
- `ticket-detail`: the strip marks "בטיפול" active for both stored statuses with a small `[data-waiting-sub]` label; the toggle `[data-waiting-toggle]` sits under the strip and posts through the existing
  `POST .../status` (`{to, revision}`). `ticket-card`, `tickets-table` (chip, menu, aria label) and `device-tickets-tab` use `chipLabel`. The filters (`open`/`handling`/... groups, `ORDER`) are by stored status
  and unchanged, so the "בטיפול" filter and the counts still include the sub-state; there is no bulk status action.
- Vendor page (`frontend/src/public-ticket`): the status radios are acknowledged / in_progress / done; `partToggle` (state.ts) drives a toggle under "in progress". The public status model already allowed the move
  (`StatusIn.status` is a closed `Literal` containing `waiting_part`; `handler_actions.STATUS_TARGETS` and `model.may_move("link", ...)` allow acknowledged / in_progress -> waiting_part and waiting_part -> in_progress), so the
  routes, the listener allow-list and the validation did not change; the server still refuses `assigned -> waiting_part` (409). Strings `wait_mark` / `wait_back` in he / en / ar / ru (ar and ru: pending native review);
  the unused `btn_waiting_part*` strings were removed.
- Security: the strict public models are unchanged. New backend tests (`test_tickets_s4_public.py`) pin the closed value set (waiting, `waiting_part ` with a space, upper case, returned, cancelled, closed, empty, null, a list
  -> 422; an extra `waiting_reason` field -> 422), the 409 from `assigned`, and the full set / clear round trip with its events and `waiting_on = assignee`.
