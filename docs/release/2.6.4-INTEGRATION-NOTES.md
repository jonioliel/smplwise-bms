## Open risks

1. USR2 was branched from integ/260 (58 commits behind integ/263). Textual merge is clean, but semantic drift against
   2.6.1-2.6.3 code (tickets, secrets store, remote channel lists) is only covered by the full gate.
2. USR1 (delete an HA user created by Arx) and USR2 (`identity_links` local -> HA user id) were developed independently:
   deleting an HA user through USR1 does not clean or check a USR2 link to it. Needs a decision / follow-up test.
3. `pilot/USR2-P3` forked from USR2-FIX in parallel with P2 and still carries the file name `0097_local_identity.sql`;
   when it is merged, check the rename and any P3 migration (next free number is 0097).
4. TKHARDEN edits the comment of 0093, which ships in 2.6.3. The migration runner has no checksum, so it is harmless, but
   2.6.3 and 2.6.4 will carry different text for the same migration.
5. Tests that enumerate lists (notification sources, messaging module uses, remote public routes, permission labels) were
   only partly run on the merged tree (notify core, messaging accounts runtime, remote access, permissions passed); TKRFQ5
   and USR2 both extended notification lists, and the frontend unit specs were not run.
6. UI bundles in `smplwise_vms/www` are not rebuilt on this branch; the release step must rebuild them on the runner.
