## Owner decisions of 2026-10-13 (binding) and how they were applied
1. **`sync_now` on person create / update: default true.** Already so on the merged tree: `PersonSaveBody.sync_now` and the
   photo body default `True` (`routers/access_control.py`, `routers/access_control_writes.py`); the editor's primary button is
   "save and sync", "save" without a sync stays as the secondary one. No change needed; recorded in the CHANGELOG.
2. **`access.call` (talk): the operator role in addition to site_admin / system_admin; `rbac.STATION_PERMISSIONS` lists
   `access.pin.generate`, `access.people.message`, `access.call`; calls / announcements consistent with S12 / S18.**
   Commit `9845d97d`:
   - `roles.json` and `contracts/examples/role-catalog.design.json`: operator gains `access.call`.
   - `rbac.STATION_PERMISSIONS` gains the three permissions (a station-scope role may carry them).
   - The call signal (`POST /intercom/stations/{id}/call`), the announcement (`POST /intercom/stations/{id}/tts`) and the TTS
     engine list (`GET /intercom/tts/engines`) moved from `access.release` at installation scope to `access.call`: the gate is
     `access.call` anywhere a station can be (on a read connection before the body, audited as `access.call` denied), then the
     named station's chain (`_call_station`: 403, audited as not sent). This is what S12 ("`access.call` gate = S11") and S18
     ("S11 moves call / announcement onto `access.call`") assumed and what S11 had left open. The now unused
     `_releaser` / `_releaser_ro` were removed; `access.release` is the door permission alone (its label no longer names calls
     or announcements).
   - Frontend: the stations screen offers call / announce / talk by `access.call` held anywhere (`rightsOf(can, policy,
     canAnywhere)`), the door by `access.release`; the old entry center (`wiskey-overview.ts`) offers calls and the
     announcement by `access.call`; the door-grant question (`GRANT_ALSO`) no longer says the grant includes calls and
     announcements.
   - Consequence (behaviour change, in the CHANGELOG as (13)): `door_opener` (CR-033: `access.read` + `access.release` only, kept
     as WXD defines it) and custom roles with the door grant alone no longer answer calls or announce; operators gain them. The
     operator stays on the default delegation allow-list, so a delegated administrator can now hand out call rights through it.
3. **Permissions assignable to any custom role; no role-name checks.** Verified: `access.pin.generate`,
   `access.people.manage` / `.sensitive` / `.message`, `access.cards.capture`, `access.call` and the bulk permissions
   (`devices.control_bulk`, `media.bulk`) are permission checks only; none is in `SYSTEM_PERMISSIONS`, so a custom role may list
   them (sensitive ones in its explicit sensitive list). The role-name checks found in the tree are restrictions, not grants
   (`door_authority`: a kiosk never opens a door; delegation never hands out `system_admin` / `site_admin`; the door-grant card
   answers "never" for viewer / kiosk) or configurable (`automations.code_view_roles`, an admin setting listing roles). New
   test `test_calls_and_announcements_ride_access_call_in_any_role` (custom role with `access.call` answers; door-only custom
   role refused; a station-scoped binding acts on its own station only).
4. **`access.station_media` settings control:** not built by S18 (the setting is changed through `PATCH /settings`); recorded
   as a follow-up and in the known limits.
5. **Door opening from automations: required eventually, kept refused in 2.4.9.** The run / enable refusals now say plainly
   that the item opens an access-control door, that opening doors from automations is not supported yet and (enable) that
   switching it off is allowed (`services/door_run_guard.py`; tests `test_wiskey_door_enable`, `test_wiskey_door_inventory`
   pin the texts). The structure already makes lifting it one change: D10a installs a `ConversionSource`
   (`door_run_guard.set_conversion_source`) once WisKey's W1 trusted-caller appendix for an automation actor exists; a
   converted item then runs and its doors open through the one door path with the real operator. No bypass was built.
6. **Release notes:** bilingual; the sub-tab name is "מתגי מסכי כניסה" everywhere in 2.4.9 (and `2.4.8-RELEASE-NOTES.md`
   now uses it too - 12 occurrences of the old "בקרות כניסה"); the 2.4.7 `dpr_cap` known limit is dropped (the ST7 section
   says so); WhatsApp master switch OFF, native screens OFF (embedded panel) by default; no physical door action is executed
   by tests.
