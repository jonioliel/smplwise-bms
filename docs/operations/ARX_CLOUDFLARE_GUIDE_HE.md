# מדריך: SmplWise Arx מאחורי Cloudflare Tunnel

Source: original

> מדריך לבעלים ולמתקינים באתרי לקוחות: חשיפת SmplWise Arx (‏`/arx`) לצד Home Assistant דרך מנהרת
> Cloudflare ייעודית ל-Arx ושם מארח אחד. מבוסס על `docs/changes/CR-008-ARX-REMOTE-APP_HE.md` §2/§4/§6-§7/§7.2
> ועל תיעוד Cloudflare Zero Trust ותוסף Cloudflared (brenner-tobias) נכון ל-29.09.2026. לוח הבקרה של
> Cloudflare משתנה מעת לעת — איפה שהניסוח עלול להשתנות מצוין במפורש בצעד עצמו.
>
> **עדכון 29.09.2026 אחה"צ:** §0 להלן הוא התוספת המחייבת החדשה — Arx עבר למודל של **דומיין ייעודי ומנהרה
> שנייה** (ולא שם מארח נוסף על `smplwise.com`). §2-§8 (שנכתבו לפני העדכון) עדיין מתארים נכון את המכניקה
> הטכנית של Cloudflare/cloudflared (יצירת מנהרה, מסלולים, הפעלת גישה מרחוק) — רק להחליף בכל מקום שבו כתוב
> "הדומיין של הלקוח" / `smplwise.com` בדומיין הייעודי `<arx-domain>` של §0, ולזכור ש**זו מנהרה שנייה**, לא
> המנהרה הקיימת של `home-<customer>`. §9 מוסיף את שתי רמות האוטומציה.

## 0. מודל הדומיין והמנהרה (עדכון הבעלים, 29.09.2026 אחה"צ)

`smplwise.com` הוא התחום (zone) הקיים של הבעלים ב-Cloudflare, ומשרת **גם מוצרים אחרים** על אותו חשבון:
`home-<customer>` (ה-HA של הלקוח עצמו) ו-`sw-ems-<customer>` (מערכות ניטור אנרגיה). טוקני API של Cloudflare
מוגבלים לכל היותר לרמת תחום שלם, לא לשם מארח בודד — ולכן אוטומציה של Arx (§9) **אסור שתרוץ מול `smplwise.com`**,
ומנהרת/רשומות `home-<customer>` **לא נוגעים בהן** בשום שלב במדריך הזה. זה משנה את הארכיטקטורה שבתרשים ובצעדים
להלן משם-מארח-נוסף-על-אותו-דומיין למודל הבא:

```
דפדפן / אפליקציה
      │  HTTPS, שם מארח ייעודי ל-Arx (סכימת ברירת מחדל: ecc.<arx-domain>)
      ▼
   Cloudflare (Edge) — תחום <arx-domain> נפרד, לא smplwise.com
      │  מנהרת Cloudflare שנייה, ייעודית ל-Arx (QUIC/HTTP2, יוצאת בלבד)
      ▼
 תוסף Cloudflared (אותו תוסף/מופע ששרת עד היום את home-<customer>.smplwise.com — ראו D13/§3)
      │
      ├─ נתיב ‎/arx/*  ──▶  SmplWise Arx  (שם מארח פנימי, ראו §2.5)
      └─ כל נתיב אחר  ──▶  Home Assistant Core  (‏homeassistant:8123)

home-<customer>.smplwise.com נשאר בדיוק כפי שהוא היום — משרת רק HA, על התחום smplwise.com,
דרך אותה מנהרה (במצב מומלץ D13-א) או מנהרה קיימת נפרדת (D13-ב, לא מומלץ).
```

- **דומיין ייעודי (D11, CR-008 §7.2):** Arx מקבל דומיין משלו (הבעלים ירכוש; `<arx-domain>` במדריך זה),
  כתחום (zone) נפרד באותו חשבון Cloudflare, עם טוקן API מוגבל ל-`Zone:DNS:Edit` על אותו תחום בלבד +
  `Account:Cloudflare Tunnel:Edit`.
- **מנהרה שנייה לכל לקוח (D12):** שם מארח `<customer>.<arx-domain>` (ברירת מחדל `ecc.<arx-domain>`), אותו
  מודל דו-מסלולי כמו קודם — `/arx` ראשון, `/` (HA) שני, אותו מקור (origin) אחד לצורך WisKey/כניסת HA
  (CR-008 §3b/D6). ה-Path **לא** מוסר בדרך; ניתוב לפי Path אפשרי **רק** במנהרה בניהול טוקן — זה לא השתנה,
  ראו §1.
- **תוסף Cloudflared אחד, במצב טוקן (D13):** אין תוסף Cloudflared נפרד ל-Arx. שתי אפשרויות הושוו:
  **(א) מומלץ** — המנהרה **החדשה** (הייעודית ל-Arx) נושאת **גם** את `home-<customer>.smplwise.com` **וגם**
  את `<customer>.<arx-domain>`; מנהרה אחת, מופע תוסף אחד; שם המארח הישן עובר אליה ב-CNAME **ידני**
  ב-`smplwise.com` (הבעלים מבצע בעצמו — לא הסקריפט, ראו §9); **(ב)** להשאיר את המנהרה הישנה כפי שהיא
  ולהריץ מופע Cloudflared שני ייעודי ל-Arx — **עובדה מאומתת**: Supervisor מזהה תוסף מותקן לפי ה-slug שלו
  בתוך המאגר (repository) שממנו הוא בא, וכיום ניתן להתקין תוסף נתון ממאגר מסוים **פעם אחת בלבד**; הדרך
  היחידה לעקוף זאת היא **פיצול (fork) של מאגר התוסף עם slug שונה** — לא משהו שמבקשים מהבעלים או ממתקין
  לבצע בכל אתר לקוח. **(א) הוא המסלול המומלץ** ומה שהצעדים בהמשך המדריך מניחים, אלא אם צוין אחרת.
- הלקוח הקיים היחיד שכבר במצב `smplwise.com` (הבעלים עצמו, `ecc.smplwise.com`) הוא **תרחיש ב׳** (§3) —
  שם מדובר במיגרציה למודל הזה, לא בהתקנת לקוח חדש (§2).

## 1. מכניקת הניתוב (path routing) — לא השתנתה

התרשים ב-§0 מראה את המודל המעודכן (דומיין ייעודי, מנהרה שנייה); העובדות הטכניות הבאות על **איך** הניתוב
עצמו עובד בתוך מנהרה בודדת נכונות בדיוק כפי שהיו לפני העדכון, בלי קשר לאיזה דומיין/מנהרה מדובר:

```
דפדפן / אפליקציה
      │  HTTPS, שם מארח אחד (למשל ecc.<arx-domain>)
      ▼
   Cloudflare (Edge)
      │  Cloudflare Tunnel (QUIC/HTTP2, יוצא בלבד מהצד של HA)
      ▼
 תוסף Cloudflared (HA add-on, ברשת hassio הפנימית)
      │
      ├─ נתיב ‎/arx/*  ──▶  SmplWise Arx  (‏0b8c26d5-smplwise-vms:8099)
      └─ כל נתיב אחר  ──▶  Home Assistant Core  (‏homeassistant:8123)

מדיית WebRTC (וידאו חי): לא עוברת דרך המנהרה — זרימה ישירה
דפדפן ⇄ go2rtc, רק האיתות (signalling) עובר בתוך /arx.
```

- שם המארח (subdomain+domain) הוא **אחד בלבד** לשני היעדים; ה-Path הוא מה שמבדיל ביניהם. זה מה שמאפשר
  ל-Arx ול-HA לשתף מקור (origin) אחד — WisKey מוטמע ומתחבר בלי כניסה שנייה (ראו CR-008 §3b).
- ה-Path **לא** מוסר בדרך: cloudflared מעביר את הבקשה המלאה (כולל `/arx/...`) הלאה; ה-service שלנו כבר
  בנוי לצפות לקידומת הזו (`SW_PUBLIC_PATH`, ברירת מחדל `/arx`).
- ניתוב לפי Path אפשרי **רק** במנהרה בניהול טוקן (Remote-managed tunnel, `tunnel_token`). מצב "options"
  של התוסף (`external_hostname`/`additional_hosts`) לא יודע לכתוב כלל עם Path — ראו תרחיש ב׳ להלן.

## 2. תרחיש א — לקוח חדש (אין עדיין Cloudflare)

### 2.1 חשבון ודומיין

> **לפי §0:** `<arx-domain>` הוא דומיין **אחד**, ייעודי ל-Arx, ולא דומיין נפרד לכל לקוח. הצעדים 1-2 כאן
> רצים **פעם אחת בלבד** — כשהבעלים רוכש ומוסיף את `<arx-domain>` לחשבון Cloudflare לראשונה. עבור כל לקוח
> חדש נוסף אחרי זה, `<arx-domain>` כבר **Active**, ומדלגים ישר ל-§2.2 (יצירת מנהרה) עם תת-הדומיין של אותו
> לקוח (`<customer>.<arx-domain>`) — בין אם ידנית לפי הצעדים להלן ובין אם דרך `scripts/provision_customer.py`‏
> (§9, Level 1, אחרי ה-MVP).

1. ליצור חשבון Cloudflare (או להשתמש בקיים).
2. להוסיף את הדומיין של הלקוח לחשבון (Add a site) ולעדכן את ה-Nameservers אצל רשם הדומיין לפי ההוראות
   שהלוח מציג. לחכות שהדומיין יעבור לסטטוס **Active**.

### 2.2 יצירת מנהרה בניהול טוקן

3. בלוח הבקרה: **Zero Trust → Networking → Tunnels → Create a tunnel**.
4. לבחור **Cloudflared** כסוג המחבר (connector), **Next**.
5. שם למנהרה (למשל `<site>-ha`), **Save tunnel**.
6. במסך ההתקנה: **לא** להריץ את פקודת ההתקנה שהלוח מציע (זה מיועד להתקנה עצמאית של cloudflared, לא
   לתוסף HA). להעתיק רק את הטוקן — המחרוזת הארוכה שמתחילה ב-`eyJ…` שמופיעה בתוך הפקודה, או ללחוץ על
   **Refresh** / להעתיק אותה מהעמוד **Overview** של המנהרה מאוחר יותר.
7. **Next / Save** כדי לסיים את יצירת המנהרה בלוח (היא תישאר "Inactive" עד שהתוסף ירוץ בשלב 2.3).

### 2.3 התקנת תוסף Cloudflared ב-Home Assistant

8. ב-HA: **הגדרות → תוספים → חנות התוספים**, לחפש **Cloudflared** (מאגר brenner-tobias), להתקין.
9. בלשונית **Configuration** של התוסף: להזין את השדה `tunnel_token` עם הטוקן משלב 2.2.6. שאר השדות
   (`external_hostname`, `additional_hosts`, `catch_all_service`, `nginx_proxy_manager`, `tunnel_name`)
   מתעלמים מעצמם כש-`tunnel_token` מוגדר — אין צורך למחוק אותם, אבל גם אין טעם למלא אותם.
10. **Start** את התוסף, לוודא בלשונית **Log** שמופיעה שורה מהצורה "Using Cloudflare Remote Management
    Tunnel" ואז "Connection registered" (או ניסוח דומה) בלי שגיאות.
11. בלוח הבקרה: לוודא שהמנהרה עברה לסטטוס **Healthy** (‏Networking → Tunnels).

### 2.4 שני המסלולים (Routes)

12. באותה מנהרה: לשונית **Routes → Add a public hostname** (בחלק מהגרסאות מופיע כ-**Add route →
    Published application**).
13. **מסלול ראשון** (חייב להיות **מעל** המסלול הריק בטבלה — סדר הבדיקה הוא מלמעלה למטה, ההתאמה הראשונה
    מנצחת):
    - **Subdomain**: תת-הדומיין של הלקוח (למשל `ecc`).
    - **Domain**: הדומיין מהתפריט הנפתח.
    - **Path**: `^/arx(/.*)?$` (regex בתחביר Go; תופס גם `/arx` בלי לוכסן בסוף וגם `/arx/...`).
    - **Service → Type**: `HTTP`. **Service → URL**: `0b8c26d5-smplwise-vms:8099` (איך למצוא את שם
      המארח הנכון אצל הלקוח הזה — ראו §2.5).
    - **Save route**.
14. **מסלול שני** (ריק, "תפיסת-כול" לשם הזה): **Add route** נוסף באותה מנהרה:
    - **Subdomain**/**Domain**: אותם ערכים כמו במסלול הראשון.
    - **Path**: להשאיר **ריק**.
    - **Service → Type**: `HTTP` (או `HTTPS` אם HA עצמו מוגדר עם תעודת TLS — במקרה כזה לסמן גם
      **No TLS Verify** באזור **Additional application settings → TLS**, כי לרוב מדובר בתעודה עצמית-
      חתומה מקומית). **Service → URL**: `homeassistant:8123` (או `:8443`/הפורט שהוגדר ב-HA אם שונה).
    - **Save route**.
15. לוודא בטבלת ה-Routes שהמסלול עם `/arx` מופיע **לפני** המסלול הריק. אם ההיפוך קרה (Cloudflare
    לפעמים ממיין לפי זמן יצירה) — למחוק את שני המסלולים וליצור מחדש לפי הסדר הנכון, או לגרור לסדר הרצוי
    אם הלוח מאפשר (בחלק מהגרסאות הסדר בטבלה נקבע אוטומטית ואינו גריר-ושחרר; יש למחוק וליצור מחדש).
16. **הגדרות מומלצות** (באזור **Additional application settings** בעת הוספת/עריכת מסלול):
    - **HTTPS only**: מופעל (מכריח את הדפדפן להשתמש ב-HTTPS מול Cloudflare; לא קשור ל-TLS מול המקור).
    - **No TLS Verify**: מופעל **רק** במסלול השני אם HA מגיש TLS בעצמו עם תעודה שאינה מאומתת פומבית;
      במסלול הראשון (Arx, `http://`) השדה הזה לא רלוונטי.
    - **WebSocket**: תמיכה ב-WebSocket מופעלת כברירת מחדל בשירותי HTTP/HTTPS של Cloudflare Tunnel —
      אין צורך להפעיל ידנית; חשוב לוודא שהיא **לא כבויה** (השדה מופיע תחת Additional application
      settings → HTTP Settings ברוב הגרסאות).
    - **HTTP/2 Origin**: לא נדרש (המקור — Arx ו-HA — לא דורש HTTP/2; להשאיר כברירת המחדל).
    - הערת אימות: הניסוח המדויק של שמות השדות באזור Additional application settings (למשל "No TLS
      Verify" מול "TLS Verification") השתנה בין גרסאות לוח הבקרה של Cloudflare ולא אומת מול הלוח החי
      בזמן כתיבת המדריך — אם שם שדה לא נמצא בדיוק כפי שכתוב כאן, לחפש לפי המשמעות (אימות תעודת TLS של
      המקור).

### 2.5 איתור שם המארח הפנימי של Arx

17. ב-HA: **הגדרות → תוספים → SmplWise Arx → Info** (לשונית המידע העליונה של דף התוסף) — שם המארח
    הפנימי של התוסף מוצג שם.
18. חלופה מדויקת יותר (דורשת תוסף SSH & Terminal פעיל, או Terminal & SSH מהתפריט המתקדם): להריץ
    `ha addons info <slug>` ולקרוא את השדה `hostname` בפלט (`<slug>` נראה בכתובת ה-URL של דף התוסף,
    למשל `0b8c26d5_smplwise_vms`).
19. הכלל הכללי: `<repository_prefix>-smplwise-vms` כש-`_` בשם המאגר הופך ל-`-`. הקידומת (`0b8c26d5` וכו')
    **תלויה במאגר ההתקנה של הלקוח** — אסור להניח שהיא זהה בין לקוחות; תמיד לאמת בפועל (שלבים 17-18).
    עותק שנבנה מקומית (בדיקות/פיתוח) יופיע כ-`local-smplwise-vms`.

### 2.6 הפעלת גישה מרחוק ב-Arx

20. ב-HA: **הגדרות → תוספים → SmplWise Arx → Configuration**: להפעיל `remote_access: true` (ברירת
    המחדל היא `false`). `remote_path` להשאיר `/arx` אלא אם יש סיבה לשנות (ראו §5).
21. **Save**, **Restart** לתוסף.

### 2.7 אימות

| # | בדיקה | תוצאה צפויה |
|---|---|---|
| 1 | לפתוח `https://<host>/` | ממשק Home Assistant הרגיל |
| 2 | לפתוח `https://<host>/arx` | מסך ההתחברות של SmplWise Arx (לא HA) |

## 3. תרחיש ב — לקוח קיים במצב options (כמו הבעלים היום)

> **זו בדיוק המיגרציה של D13-א (§0):** המנהרה **החדשה** שנוצרת בשלב 2 להלן היא המנהרה היחידה שתישאר —
> היא נושאת גם את שמות המארח הישנים על `smplwise.com` (שלבים 3-4, ללא שינוי) וגם את שם המארח החדש
> והייעודי `<customer>.<arx-domain>` (שלב 5 המעודכן) ל-Arx. ה-CNAME של `smplwise.com` מוחלף כאן **ידנית**
> על ידי הבעלים (שלב 3) — זו בדיוק הפעולה הידנית ש-D13 מתאר; `<arx-domain>` חייב כבר להיות **Active**
> בחשבון (§2.1) לפני שמתחילים כאן.

**איתור המצב הנוכחי:** בלשונית **Log** של תוסף Cloudflared — שורה "Using Cloudflare Remote Management
Tunnel" = כבר במצב טוקן, לדלג לתרחיש ג׳; שורה עם `ingressRule=0 originService=http://homeassistant:…`
(או ללא אזכור "Remote Management") = מצב options, להמשיך כאן.

**השבתה זמנית:** במהלך הצעדים 4-9 להלן, לפני שהמנהרה החדשה עולה, גישה מרחוק לשם המארח הציבורי (וגם ל-HA
עצמו) **לא תעבוד**. במעבדה/בבית הלקוח זה בדרך כלל 10-20 דקות; גישה מקומית (ברשת הבית) לא מושפעת.

1. לתעד את התצורה הנוכחית של התוסף לפני נגיעה בה: לצלם מסך או להעתיק לקובץ טקסט את הערכים המלאים של
   `external_hostname`, כל רשומות `additional_hosts` (hostname + service לכל אחת), `catch_all_service`,
   `nginx_proxy_manager`, `tunnel_name`. זה מה שמשמש לשחזור אם צריך לחזור אחורה (שלב 10).
2. **Zero Trust → Networking → Tunnels → Create a tunnel → Cloudflared** — שם חדש (למשל `<site>-ha`,
   שונה משם המנהרה הישנה שהתוסף יצר אוטומטית). להעתיק את הטוקן (כמו §2.2.6), **לא** להריץ את פקודת
   ההתקנה.
3. **מחיקת ה-CNAME הישן קודם:** ‏**DNS → Records**, לאתר את רשומת ה-CNAME של תת-הדומיין (`ecc` וכו')
   שמצביעה על המנהרה הישנה (‏`<tunnel-id>.cfargotunnel.com`), **Delete**. בלי המחיקה הזו לוח הבקרה
   מסרב ליצור מסלול חדש לאותו שם — הוא כבר "תפוס" ע"י ה-CNAME.
4. ליצור מחדש כל רשומה מהתיעוד בשלב 1 כמסלול (Route) על המנהרה החדשה, לפי §2.4 שלב 13 (Subdomain,
   Domain, Path ריק אלא אם הרשומה המקורית הייתה `additional_hosts` עם hostname נפרד — במקרה כזה
   Subdomain שונה, לא Path), Service Type/URL תואמים למה ש-`service:` היה. אם היה `catch_all_service`
   או ניתוב ל-NPM (`nginx_proxy_manager`) — להוסיף גם אותו כמסלול Service מתאים.
5. **על אותה מנהרה החדשה, להוסיף שני מסלולים נוספים לשם המארח הייעודי** `<customer>.<arx-domain>` (למשל
   `ecc.<arx-domain>` — **דומיין נפרד מ-`smplwise.com`**, לא תת-דומיין/Path על אחד משמות המארח שתועדו
   בשלב 1): מסלול ראשון Path `^/arx(/.*)?$`‏ → `0b8c26d5-smplwise-vms:8099` (לאתר את הקידומת לפי §2.5),
   ומסלול שני Path ריק → `homeassistant:8123` — בדיוק כמו §2.4 שלבים 13-14, רק על ה-Subdomain/Domain של
   `<arx-domain>` במקום `smplwise.com`.
6. לוודא בטבלת Routes: עבור `<customer>.<arx-domain>` — `/arx` **לפני** המסלול הריק (כמו §2.4.15); עבור כל
   שם מארח על `smplwise.com` (מה ששוחזר בשלב 4) — הסדר וההתנהגות **ללא שינוי** לעומת לפני המיגרציה (Arx לא
   מנתב שם כלל).
7. תצורת תוסף Cloudflared: להחליף ל-`tunnel_token: <הטוקן משלב 2>`, **Save**. שאר השדות (השלב 1)
   נשארים בתצורה אבל מתעלמים מעצמם — אין חובה למחוק אותם, מותר להשאיר לתיעוד.
8. **Restart** לתוסף. בלשונית Log לוודא "Using Cloudflare Remote Management Tunnel" בלי שגיאות, ושהמנהרה
   הישנה (אם עדיין קיימת ברשימה) לא מקבלת תעבורה.
9. לוודא ששני שמות המארח עובדים: `https://home-<customer>.smplwise.com/` (או השם הישן הרלוונטי) עדיין
   פותח HA כרגיל, **ו-** `https://<customer>.<arx-domain>/` פותח HA (מסלול ה-catch-all של שלב 5) — ורק
   אז להמשיך ל-§2.5-§2.7 (איתור hostname הפנימי, הפעלת `remote_access`, אימות `/arx` על שם המארח הייעודי).
10. **נסיגה (rollback) אם משהו נשבר:** בתצורת התוסף למחוק את `tunnel_token`, למלא בחזרה את הערכים
    מהתיעוד בשלב 1 (`external_hostname` וכו'), **Save**, **Restart** — התוסף חוזר למצב options עם
    המנהרה האוטומטית הישנה שלו (cloudflared בונה מנהרה חדשה באותו שם אוטומטי אם הישנה נמחקה בלוח).
    אם ה-CNAME על `smplwise.com` נמחק בשלב 3 ולא נוצר מחדש אוטומטית — להוסיף אותו ידנית לפי מה שתועד
    בשלב 1, או לפנות לתמיכת Cloudflare אם הרשומה האוטומטית לא חוזרת. **בנוסף:** למחוק את רשומת ה-CNAME
    של `<customer>.<arx-domain>` בתחום `<arx-domain>` (נוצרה בשלב 5) ואת שני המסלולים שלה במנהרה החדשה,
    כדי לא להשאיר שם מארח "יתום" שמצביע על מנהרה שהתוסף כבר לא משתמש בה.

## 6. אבטחה מומלצת

### 6.1 בצד Cloudflare (אופציונלי, לפי החלטת הבעלים — לא בוצע כברירת מחדל)

- **WAF Managed Rules**: **Security → WAF → Managed rules**, להפעיל את ה-**Cloudflare Managed
  Ruleset** על הדומיין (חוסם דפוסי תקיפה ידועים לפני שהם מגיעים למנהרה).
- **Rate limiting על נתיב ההתחברות**: **Security → WAF → Rate limiting rules → Create rule**.
  - Matching expression: `(http.request.uri.path matches "^/arx/api/v1/auth/.*")`.
  - Requests: **10** ל-**60 שניות** (ערך מוצע לפעולת Log/Challenge), ו/או כלל שני מחמיר יותר — **30**
    ל-**3600 שניות** (Block) — לעצור ניחוש סיסמאות ממושך בלי לחסום משתמש לגיטימי שטעה כמה פעמים.
  - Action: **Challenge** (ולא Block ישירות) מומלץ בסיבוב ראשון, כדי לא לחסום משתמשים אמיתיים בטעות;
    לעבור ל-Block אחרי בדיקה שהכלל לא תופס תעבורה לגיטימית.
- **Bot Fight Mode**: **Security → Bots**, להפעיל (זמין גם בתוכנית Free) — חוסם בוטים ידועים שמנסים
  להתחבר.
- **Cloudflare Access (עתידי, D3 ב-CR-008 — עדיין לא הוחלט):** **Zero Trust → Access → Applications →
  Add an application → Self-hosted**, עם Path התואם ל-`/arx`, ומדיניות (Policy) לפי אחת מהאפשרויות
  שנשארו במפת הדרכים: קוד חד-פעמי בדוא"ל (One-time PIN) לכל משתמש מורשה, או הגבלה למנהלים בלבד
  (למשל לפי קבוצת אימייל). זו שכבת אימות **נוספת לפני** מסך ההתחברות של Arx, לא תחליף לו — להפעיל רק
  אחרי החלטת בעלים מפורשת, כי היא דורשת שכל משתמש יעבור גם דרכה.

### 6.2 בצד Home Assistant

- **סף חסימת כניסות (מוצע, לא חובה — D9 ב-CR-008 עדיין ממתין):** ב-HA מגרסה 2026.8 ואילך ההגדרה עברה
  מ-`configuration.yaml` ללוח: **הגדרות → מערכת → רשת**, שדה **Login attempts before ban** (המקביל ל-
  `login_attempts_threshold` בגרסאות ישנות/ב-YAML) — ערך מוצע **10**. ברירת המחדל של HA היא ללא חסימה
  (`-1`). שדה **Enable IP banning** (`ip_ban_enabled`) מופעל כברירת מחדל. **סיכון לתעד למתקין**: חסימת
  IP ב-HA חוסמת את אותה כתובת גם ל-`/arx` וגם ל-HA עצמו, עד הסרה ידנית מ-`ip_bans.yaml` (או מהלשונית
  המקבילה בלוח) — משתמש לגיטימי מאחורי NAT משותף (משרד, לקוח סלולרי) עלול להיחסם בטעות אם מישהו אחר
  מאותה כתובת טעה הרבה פעמים.
- **Trust X-Forwarded-For / Trusted proxies**: תוסף Cloudflared כבר דורש את זה בשביל עצמו (כדי ש-HA
  יראה את ה-IP האמיתי של המבקר ולא את כתובת התוסף) — **הגדרות → מערכת → רשת**, שדה **Trust
  X-Forwarded-For** (`use_x_forwarded_for`) מופעל, ו-**Trusted proxies** (`trusted_proxies`) כולל
  `172.30.33.0/24` (טווח כתובות התוספים ב-Supervisor, מכיל גם את Cloudflared וגם את Arx). זו הגדרה
  קיימת ולא צעד חדש ל-Arx — אם היא כבר מוגדרת בשביל Cloudflared (נדרשת בתיעוד התוסף עצמו), Arx נהנה
  ממנה אוטומטית: בקשות המשתמש דרך `/arx` מזוהות עם ה-IP האמיתי גם ביומני HA (למשל בכשלונות התחברות
  שנרשמים דרך `/auth/login_flow`, ‏`/auth/token`).
- **MFA (אופציונלי, D8 ב-CR-008 עדיין ממתין):** לא חובה כברירת מחדל; ההמלצה השמורה ב-CR-008 היא לחייב
  MFA למשתמשים מרוחקים עם תפקידי ניהול (`site_admin`/`system_admin`) — להפעיל דרך **פרופיל המשתמש →
  אבטחה מדו-שלבית** בכל משתמש רלוונטי ב-HA.

## 9. אוטומציית פרוביזיינינג לקוחות (Level 1 / Level 2, D14 ב-CR-008 §7.2)

שני הצעדים הידניים החוזרים ביותר בתרחישים א׳-ג׳ לעיל — יצירת מנהרה/הגדרת ה-ingress שלה, ויצירת רשומת ה-CNAME
של `<customer>.<arx-domain>` — ניתנים לאוטומציה בשתי רמות. שתיהן פועלות **רק** מול התחום הייעודי
`<arx-domain>` (§0/D11); אף אחת מהן לא נוגעת ב-`smplwise.com`.

### 9.1 Level 1 — סקריפט מקומי (אחרי ה-MVP, ‏≈2 שעות בנייה)

`scripts/provision_customer.py <customer>` — הבעלים מריץ מהמחשב שלו, עם טוקן Cloudflare API המוגבל
ל-`Zone:DNS:Edit` על `<arx-domain>` בלבד + `Account:Cloudflare Tunnel:Edit`, נקרא מ-`secrets/` (**לעולם לא**
מוזן/מודבק בצ'אט, ב-commit, בקובץ תיעוד או בלוג — זהה לכלל הקיים על `secrets/lab.env`).

הסקריפט מבצע שלוש קריאות API (Cloudflare, אומתו 29.09.2026 מול `developers.cloudflare.com/api/resources/
zero_trust/subresources/tunnels/` ומשאב רשומות ה-DNS של התחום):

1. **יצירת מנהרה** — `POST /accounts/{account_id}/cfd_tunnel`
   ```json
   {"name": "<customer>-arx", "config_src": "cloudflare"}
   ```
2. **הגדרת ה-ingress** — `PUT /accounts/{account_id}/cfd_tunnel/{tunnel_id}/configurations`
   ```json
   {"config": {"ingress": [
     {"hostname": "<customer>.<arx-domain>", "path": "^/arx(/.*)?$", "service": "http://<addon-host>:8099"},
     {"hostname": "<customer>.<arx-domain>", "service": "http://homeassistant:8123"},
     {"service": "http_status:404"}
   ]}}
   ```
3. **רשומת ה-DNS** — `POST /zones/{zone_id}/dns_records`
   ```json
   {"type": "CNAME", "name": "<customer>.<arx-domain>", "content": "<tunnel_id>.cfargotunnel.com", "proxied": true}
   ```

לאחר ההרצה: מדפיס את טוקן המנהרה למסך (להזין ידנית ב-`tunnel_token` של תוסף Cloudflared — §2.3/§3.7/§4,
לפי התרחיש). אידמפוטנטי — לפני יצירה מחפש מנהרה קיימת בשם `<customer>-arx`. תומך ב-`--dry-run` (מדפיס את
שלוש הקריאות בלי לשלוח אותן) וב-`--remove` (מוחק את רשומת ה-DNS ואז את המנהרה, בסדר ההפוך).

### 9.2 Level 2 — כפתור באשף ההתקנה (P2.5, ‏≈2-3 ימים כולל השירות)

פעולת "**הפעל גישה מרחוק**" באשף ההתקנה של Arx: קוראת לשירות פרוביזיינינג קטן שמארח SmplWise (Cloudflare
Worker או שרת קטן, מחזיק את טוקן `<arx-domain>` ורישום רישיונות לקוחות) ומקבלת חזרה **רק** את טוקן המנהרה
של אותו לקוח — לעולם לא טוקן ברמת החשבון. Arx כותב את הטוקן לתוך אופציות תוסף Cloudflared עצמו דרך ה-API
של ה-Supervisor (‏`POST /addons/<slug>/options` ואז restart) ומציג את סטטוס החיבור באשף — בלי מעבר ללוח
הבקרה של Cloudflare או ללשונית Configuration של Cloudflared בכלל.

**דורש `hassio_role: manager`** ב-`config.yaml` של Arx (במקום התפקיד הצר יותר של היום). **המשמעות
האבטחתית, במפורש:** תפקיד `manager` מאפשר ל-Arx לקרוא ולכתוב את האופציות ולהפעיל/לעצור/להפעיל-מחדש **כל**
תוסף במארח — לא רק את Cloudflared — רדיוס נזק גדול משמעותית אם Arx עצמו ייפרץ. זו הרחבת הרשאה מאותה קטגוריה
כמו כתיבה ל-NVR/go2rtc/משתמשי HA/הגדרות רשת (`AGENTS.md`/`CLAUDE.md`, סעיף Process) ולכן דורשת אישור מפורש
וממוקד-משימה מהבעלים **לפני** מימוש, בנפרד מכל משימת "תיעוד" או "MVP" כללית. Level 2 רשום כאן כמתוכנן בלבד —
לא התחיל מימוש.
