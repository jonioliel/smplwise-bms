# Soak ללא התקנים (device-free) — T068

**מה זה:** `smplwise_vms/backend/tests/soak/soak_local.py`, בדיקת עמידות (soak) של כל ה-backend בתהליך אחד
מול NVR מדומה ו-Home Assistant מדומה שמופעלים מחדש לפי לוח זמנים. זהו החצי ללא התקנים של T068 (AT136:
soak, הפעלות מחדש של HA / NVR, תור ייצוא עם דיסק מלא, לחץ-נגד). החצי התלוי-בהתקנים — ה-NVR האמיתי, הפעלות
מחדש של go2rtc, זרמים וטרנסקוד על מארח ה-Home Assistant — נשאר ברשימת הבדיקה של המעבדה.

## איך מריצים

```
cd smplwise_vms/backend
SW_SOAK=1 python tests/soak/soak_local.py --minutes 10 --out <scratch>/soak.json
# או דרך pytest (אותה הרצה, נכשל כשבדיקה נכשלת)
SW_SOAK=1 SW_SOAK_MIN=10 SW_SOAK_OUT=<scratch>/soak.json python -m pytest tests/soak/soak_local.py -s -p no:cacheprovider
```

אפשרויות: `--nvr-every` (שניות, ברירת מחדל 120), `--ha-every` (שניות, ברירת מחדל 150), `--rss-slope-mb-h`
(ברירת מחדל 60). `SW_SOAK_TRACEMALLOC=1` מוסיף את גידול הקצאת הזיכרון המובילה של Python בין סוף החימום
לסוף ההרצה (לאבחון בלבד: tracemalloc מאט הכול מספיק כדי לעוות את מספרי המנעול וזמן התגובה).
שום דבר לא יוצא מהמחשב: הכול מאזין על 127.0.0.1, תיקיית הנתונים היא תיקייה זמנית טרייה (מוסרת בסוף
ההרצה), והסקריפט מסרב לרוץ בתוך ה-add-on (`SUPERVISOR_TOKEN`).

Python, עומקי תורים, עבודות ייצוא ממתינות; חיבורי TCP של התהליך לפי מצב כל 30 שניות.

## מה נבדק (asserted)

אחרי ההרצה, ניקוז (drain) (יש שוב מקום בדיסק, שני הפידים למעלה, עד 120 שניות) וכיבוי האפליקציה:

- אין `database is locked` ביומן ו-`db.write_lock.busy_errors` = 0; אין HTTP 500;
- שיפוע (slope) של working set ו-private bytes אחרי החימום (30% מההרצה, לפחות 60 שניות) מתחת ל-`--rss-slope-mb-h`;
- threads (מקסימום − ראשון אחרי החימום ≤ 12), handles / fds (≤ +150), חיבורי TCP (≤ 60 פתוחים, ≤ 5 ב-`CLOSE_WAIT`);
- אין thread של המוצר (`alertstream`, `alertstream-writer`, `ha-sync`, `intercom-sync`, `export-worker`,
  `event-thumbs`, `storage-warm`) חי 30 שניות אחרי הכיבוי;
- תור הקליטה (ingest) בתוך התחום שלו; `accepted = processed + failed + coalesced + dropped + depth`; כל
  התראה שנשלחה התקבלה; המאזין קרא את מה שה-NVR שלח (מסמכים שנקטעו על ידי הפעלה מחדש למעט); כשלא נזרק
  כלום, ספירות פרצי התנועה השמורות (`SUM(count)` של שורות התנועה) שוות למספר התראות התנועה - האיחוד
  (coalescing) לא מאבד כלום;
- מנויי ה-WebSocket חוזרים לאפס; עבודות ייצוא ממתינות לעולם לא מעל `MAX_QUEUED_TOTAL`;
- כל 507 שהלקוח קיבל נספר (`refused_disk`); לפחות עבודה אחת הושהתה בגלל דיסק מלא וחודשה; שום דבר לא
  נשאר בתור / רץ / מושהה אחרי הניקוז;
- שני הפידים מחוברים שוב אחרי ההפעלה מחדש האחרונה שלהם; אף לקוח soak לא נתקע.

## מגבלות

- תחנת עבודה אחת של Windows, תהליך אחד, התקנים מדומים: המספרים הם על הקוד של המוצר עצמו (תורים, מנעולים,
  threads, sockets, זיכרון), לא על ה-NVR, go2rtc או מארח ה-Home Assistant.
- עשר דקות מראות דליפות מהסוג המהיר (threads, sockets, מנויים, תורים); דליפת זיכרון איטית דורשת הרצה של
  3-5 שעות (`--minutes 240`) ולתמונה האמיתית, ה-add-on על Linux עם ה-NVR האמיתי.
- הדיסק מדומה (50 MB, `shutil.disk_usage` מוחלף עבור תיקיית הנתונים בלבד): זה מוכיח את המדיניות, לא את
  התנהגות מערכת הקבצים ב-100% מלא.
